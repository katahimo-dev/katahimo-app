# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

`katahimo-app` is the rebuild of the childcare home-visit staff webapp `gas-childcare-visit-app` (Google Apps Script, single tenant, Sheets/Drive/Calendar as the data store) as a multi-tenant web app with PostgreSQL as the source of truth. The GAS app lives in the read-only submodule `legacy/gas-childcare-visit-app` and is the **specification for business logic and calculation results** (ported behavior must match it, checked by the gasParity tests); the implementation must not copy its GAS-isms (see "Porting rules"). Screens started from the GAS app and evolve in this app on their own: their wording and behavior are defined by this app's code, there is no requirement to match GAS visually, and product decisions on screen changes are made here. The goal is a functional superset of GAS: `doc/11_GAS版との機能比較.md` lists every GAS capability (including the nightly `gas-root-serach` LINE WORKS DM this app replaces with Web Push) with a verdict 同等/改善/変更/GAS版のみ and the reason — keep it current when you add or drop a GAS-equivalent feature.

Status (2026-09-26, baseline Ver. 1.0.0-baseline + unreleased): all screens the GAS `index.html` calls are rebuilt, all server logic is ported, schedule/route runs without GAS (Google Calendar + Maps APIs), admins manage staff / AI prompts / the audit log in the app's 🛠 管理 tab instead of editing spreadsheets, coordinators and admins browse and CSV-export everyone's daily/accident reports there (📋 報告一覧, replacing reading the mirrored 日報/事故報告 sheets), staff save their 出勤簿 as Excel (one month or a fiscal year; admins also every staff's month in one file, replacing the per-staff 出勤簿 spreadsheets), staff get a next-day schedule notice by PWA Web Push, and GCP deployment (Cloud Run + Cloud SQL, Terraform) is written but not yet applied. Product decisions: spreadsheets are only a one-way mirror (never a data source to edit); customer data changes only through the RESERVA CSV import (nightly 03:00 job + admin API; no import on screen open) and the external customer ingest API (`POST /api/integrations/customers`, the receiving side for a future RESERVA/other-system integration; upsert only); in-app customer management and the actual automatic reflection from レセルバ are future work. The design docs live in `doc/` (index: `doc/README.md`); they are written against the code — when you change behavior, update the matching doc. `CHANGELOG.md` restarts at the baseline (older history is in git).

Code comments, docs, README/CHANGELOG entries and commit messages are written in **Japanese** — keep new ones in Japanese. This file is the exception (English).

The root scripts above are thin `pnpm --filter <pkg> <script>` wrappers. Relative CSV paths are resolved from the directory you ran pnpm in (`INIT_CWD`), see `packages/api/src/scripts/cliArgs.ts`.

CI (`.github/workflows/ci.yml`, doc/07 §9) runs lint → typecheck → migrate on PostgreSQL 17 (same major as Cloud SQL) → `pnpm db:generate` drift check (fails if schema changes lack a committed migration) → test (including the DB integration project) → build, then a separate `e2e` job (seeds the dev DB, builds+serves the web app, runs `tools/e2e`; CI installs its own Chromium). `infra.yml` runs `terraform fmt -check`/`validate` with the committed `infra/gcp/.terraform.lock.hcl`. The legacy submodule is fetched with `secrets.SUBMODULE_TOKEN` (only the `check` job needs it, for gasParity); without it the parity tests skip with a warning — so parity tests must tolerate a missing submodule at collection time (load GAS sources lazily, not at `describe` level).

Local DB: PostgreSQL 16+ on :5432 (`infra/initdb/00_create_database.sql` then `01_bootstrap.sql` as superuser; pass `-v dbname=<name>` to 00 for a scratch DB) or `docker compose -f infra/docker-compose.yml up -d` (:5433). `.env` from `.env.example`; minimum is `DATABASE_URL` (`katahimo_app`), `WORKER_DATABASE_URL` (`katahimo_worker`), `MIGRATION_DATABASE_URL` (`katahimo_migrator`), `SESSION_SECRET`, `SECRET_BOX_LOCAL_KEY` (64 hex). `APP_PUBLIC_URL` (worker, optional) is the login-screen URL written into the admin's password-guide mail. Without Google/Gemini/SMTP settings everything falls back to noop/console implementations; without `VAPID_PUBLIC_KEY` (API + worker) / `VAPID_PRIVATE_KEY` + `VAPID_SUBJECT` (worker; all three or none) Web Push is off (the settings screen hides 通知, `push.*` topics are skipped). Target is Cloud SQL PostgreSQL 17 (CI `postgres:17`) and it must also work on 16: don't use PG18 features (no `uuidv7()` in SQL — ids are UUIDv7 generated in the app, `core/domain/ids`; the DB default is `gen_random_uuid()`).

**pnpm 11 gotcha**: `pnpm <script> -- --opt` passes the literal `--` through to the script. Any CLI you write must drop `--` from `process.argv` before parsing (use `cliArgs()` / `takeOption()` from `packages/api/src/scripts/cliArgs.ts`; `tools/e2e/src/e2e.ts` does `argv.slice(2).filter((a) => a !== '--')`). When in doubt run the tool directly: `cd tools/e2e && npx tsx src/e2e.ts --only '^login'`.

Built `dist/` output does not bundle external deps and cannot run from the pnpm workspace `node_modules`; to run it outside Docker, install prod deps flat (`pnpm install --prod --config.node-linker=hoisted --filter '@katahimo/api...'`) next to it, like the `Dockerfile` does. `WEB_DIST_DIR` makes the API serve the built SPA (same origin, `/api/*` first).

## Architecture and conventions

### Multi-tenancy (RLS) and roles

- Every table in `public` has `tenant_id` and the policy `tenant_isolation`: `tenant_id = app_current_tenant()` where `app_current_tenant()` is `nullif(current_setting('app.tenant_id', true), '')::uuid` (the `nullif` matters: after a transaction-local setting a pooled connection reverts to `''`). No setting → no rows visible, nothing writable. `FORCE ROW LEVEL SECURITY` everywhere, so even the owner is filtered. `platform.*` (tenants, plans, rate limits, lifecycle events) has no RLS and is read-only for the app.
- Roles (doc/03 §5): `katahimo_owner` (NOLOGIN, owns everything), `katahimo_migrator` (LOGIN, member of owner, `SET ROLE` on login; migrations and `platform.provision_tenant()`), `katahimo_app` (API), `katahimo_worker` (worker/jobs; has the cross-tenant `outbox_messages_worker` policy; grants trimmed to the tables/operations jobs use — no `staff_credentials`, `tenant_secrets`, AI prompts or matching tables; `worker.integration.test.ts` runs the real jobs as this role), `katahimo_readonly` (placeholder). None has SUPERUSER/BYPASSRLS. App/worker have per-database role settings `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout`, set by `infra/initdb|cloudsql/01_bootstrap.sql` (role settings need a superuser, so not in migrations). Grants are explicit per table in `0001_baseline_custom.sql` (no default privileges); append-only tables (`care_record_revisions`, `entity_changes`, `ai_prompt_revisions`, `app_logs`) get SELECT/INSERT only. New tables need their GRANTs and `FORCE ROW LEVEL SECURITY`; `packages/db/src/integration/catalog.integration.test.ts` checks this from the catalog.
- Tenants are created only by `platform.provision_tenant()` (SECURITY DEFINER) via `core/usecases/tenantProvisioning.ts` (the app generates the tenant id). `bootstrapTenant()` there (CLI `tenant:create`) also creates the first admin.
- `tenantId` comes **only** from the session cookie, never from request bodies/queries.
- Composite keys: tenant tables have PK `(tenant_id, id)` and every FK to a tenant table is `(tenant_id, x_id) → (tenant_id, id)`. Every `tenant_id` references `platform.tenants`. Default PostgreSQL naming (`_pkey`, `_fkey`, `_idx`, `_check`, `_excl`; `constraintName()` in `schema/_columns.ts` drops `tenant_id` if a name exceeds 63 bytes).
- Types: enum-like `text` + `CHECK` (values in `core/domain/model/codes.ts`), `timestamptz` / `date` / `time`, ranges `tstzrange` / `daterange` half-open `[start, end)`, `row_version` on concurrently edited rows, `updated_at` maintained by the `set_updated_at()` trigger, `archived_at` for soft deletes, `staff.retired_on`.

### Unit of Work (all DB access)

- Usecases never touch Drizzle. They call `deps.uow.run(tenantId, async (r) => …, { actorId })` (`core/ports/unitOfWork.ts`, `db/src/uow.ts`): one transaction, tenant (and `app.actor_id` for triggers) set once, and `r` is a set of repositories bound to that transaction that **take no tenantId**. Throwing rolls everything back, including outbox rows. Never add code that needs a second pooled connection or a network call (including Cloud KMS) inside `run`.
- Domain writes and their outbox messages go in the same `run`. External calls (Calendar, Maps, Gemini, Chat, storage uploads) happen outside `run`; for uploads, put the blob first and delete it if the transaction fails (see `usecases/receipts.ts`).
- Optimistic concurrency: rows with `row_version` are updated with an expected version (`update(id, patch, expectedVersion)`); a mismatch is `DomainError('conflict')` → 409 with a Japanese "reload and retry" message. Contracts expose `rowVersion` in views and accept an optional `rowVersion` in update requests. Attendance days are also locked with `SELECT … FOR UPDATE` (`attendance.lockDay`).
- DB rejections are mapped once in `db/src/errors.ts` (`KH001` locked month, `KH002` locked record, `23P01` EXCLUDE → conflict, login-email PK → conflict).
- Tests use the in-memory `MemoryDatabase` / `FakeUnitOfWork` (rollback via snapshot) from `core/src/usecases/testDoubles.ts` and the all-in-one deps from `testContext.ts` (exported as `@katahimo/core/test-utils`).
- In raw `sql` templates inside a single-table select, Drizzle renders columns unqualified — in correlated subqueries write outer columns as `"table"."column"` explicitly (see `repositories/tenant/customers.ts`). The query builder (`notExists(...)` etc.) qualifies correctly.

### Data protection at rest

- Storage is protected by **CMEK disk encryption**: the Cloud SQL instance (disk, backups, PITR) and the GCS receipts bucket are encrypted with app-specific Cloud KMS keys (`infra/gcp/kms.tf`: key ring `katahimo`, keys `cloudsql-cmek` / `storage-cmek`, 90-day rotation, `prevent_destroy`; the Cloud SQL / GCS service agents hold `cryptoKeyEncrypterDecrypter`). Access to the data itself is narrowed by RLS, per-role grants, audit logs and rate limits (doc/06 §8). Losing/disabling a key version loses the data including backups (doc/07 §3.8).
- Personal data lives in plain typed columns (`text`, `jsonb` for `care_records.body` / `care_record_revisions.body` / `entity_changes.before`, `double precision` `lat`/`lng` pairs + `*_geo_cell` geohash; `customer_addresses.lat_lng_text` keeps the source CSV text for display, parsed by `@katahimo/shared` `parseLatLngText`); at-rest protection is CMEK plus access control — keep new columns typed (no app-level column encryption).
- Tenant secrets (Gemini API key, Google Chat webhook URLs) are the one exception: `tenant_secrets.sealed_value` is sealed by `SecretBoxPort` (`integrations/src/secret-box`: `CloudKmsSecretBox` with `SECRET_BOX_PROVIDER=gcp` / `SECRET_BOX_KMS_KEY` (key `tenant-secrets`, API SA only), `LocalSecretBox` with `SECRET_BOX_LOCAL_KEY` in dev; the ciphertext is bound to tenant id + secret name). Only the tenant-secret path uses it (`core/usecases/settings.ts` `readTenantSecret(s)` / `writeTenantSecrets`, called by admin settings, report AI and the webhook notifier), sealing/opening outside the UoW transaction. Changing the key/provider means admins re-save the secrets.
- Hashes: `sessions.token_hash` (SHA-256), `password_reset_codes.code_hash` (HMAC with a key HKDF-derived from `SESSION_SECRET`; the mail code itself sits in `mail_code` only until the worker sends it or it is used; the maintenance job clears expired ones), `rate_limit_buckets.subject_hash` (HMAC), `receipts.dedupe_hash` (SHA-256 of `buildReceiptDedupeKey`, GAS key semantics; partial UNIQUE + `ON CONFLICT DO NOTHING`; only the first of identical images in one upload carries it). Never log personal data values; `app_logs.details` holds IDs, counts and reason codes only.

### Security: admin-vs-self

Never trust a client-supplied staff id (the GAS app's rule, "never trust a client-supplied staff name", carried over). Roles are `staff` | `coordinator` | `admin` (`@katahimo/shared` `isAdminRole` / `canActForOthers`; core re-exports them):

- `requireSession(container, deniedAction?)` / `requireAdmin(container, action)` middlewares (401/403 + WARN `<action>.access_denied` log); `actorOf(c)` gives the usecase `Actor` (`{ tenantId, staffId, role, meta }`).
- `targetStaffIdOf(c, requestedStaffId)` (→ `core/domain/staff/roles.ts` `resolveTargetStaffId`) is the single helper: `staff` is forced to their own id; `coordinator`/`admin` may target another staff. Usecases re-check (`loadAttendanceTarget` throws forbidden), and report overwrites cannot change the customer or author (409 `customer_mismatch` / `author_mismatch`); staff cannot overwrite others' reports (403).
- Integration endpoints `/api/integrations/*` (`routes/integrations.ts`) are the one exception to cookie auth: `Authorization: Bearer kth_<tenantIdHex>_<random>` only (cookies are ignored), the tenant comes from the token's tenant part (RLS context) and the row is found by the SHA-256 of the whole token (`core/usecases/integrationApiKeys.ts`, same idea as the `tenantId.rawToken` session cookie); the writable customer source is fixed per key. Keys (`integration_api_keys`) are issued/revoked only by the operator CLI over `MIGRATION_DATABASE_URL`; the app role can only SELECT them and UPDATE `last_used_at` (column grant).
- Admin-only endpoints: `/api/admin/*` (staff CRUD + password-guide mail, audit logs + CSV, customer CSV import), `/api/settings/admin/*` (Gemini / Google Chat secrets, AI prompts), `POST /api/attendance/day/aggregate/refresh`, `GET /api/attendance/export/all`. Coordinator+admin (`requireCoordinator`): `GET /api/reports/export.csv`; `GET /api/reports` / `GET /api/reports/:id` are open to all staff but plain staff only get their own records (list forces `staffId` to self, others' detail is 403 + SECURITY). The web shows the staff selector and the 🛠 管理 tab (📋 報告一覧 only) for `canActForOthers(user.role)`, and admin settings + the tab's スタッフ / AIプロンプト / 操作ログ for `isAdminRole(user.role)`, but the server check is the real one. Customer CSV import and the aggregate refresh have no screen (API only).

### Logging

Use `AppLogPort.write({ tenantId, level, action, actorStaffId, targetStaffId, details, ...actor.meta })` (`core/ports/appLog.ts`, stored in the monthly-partitioned, append-only `app_logs`; `meta` carries ip, user agent and the request id). Levels `INFO | WARN | ERROR | SECURITY`. Rules (same as GAS `logToBuffer`): always log WARN/ERROR/denials and all writes; log read successes only when they cost money (Maps calls) or when an admin reads another staff's data (`targetStaffId`). Action names are dotted (`report.daily.saved`, `schedule.route.failed`). The port never throws. Process logs are one-line JSON for Cloud Logging: the API logs every request (`http/requestLog.ts`; request id = Cloud Trace id from `X-Cloud-Trace-Context` or a UUID, returned as `X-Request-Id`).

### API contracts and errors

- Request/response shapes are zod schemas in `packages/shared/src/contracts/` (queries too). The API validates input with `parseJsonBody` / `parseQuery` and returns success bodies through `jsonOk(c, schema, body)` (serialized, then parsed by the response schema — a mismatch is a 500 in the log, not a silent drift) (`api/src/http/responses.ts`); the web validates every response against the same schema in `web/src/api/client.ts`. A new endpoint needs a contract first; don't define request schemas locally in routes.
- Usecases throw `DomainError(code, message, fields?, reason?)` (`core/domain/errors/domainError.ts`); `app.onError(onApiError)` maps it once (`DOMAIN_ERROR_STATUS`): `not_found` 404, `forbidden` 403, `validation_failed` 400, `locked` 400, `conflict` 409, `rate_limited` 429, `upstream_unavailable` 502. Anything else is logged with the request id and returned as a generic `internal` 500. Errors are always `{ code, message, fields? }`; `message` is user-facing Japanese; the web shows it via `userMessageOf`. External-service failures return a generic message (details only in logs).
- Endpoint specs: `doc/04_API仕様.md` (functional rules per screen: `doc/02_機能仕様.md`) — update them with behavior changes.

### Attendance (出勤簿) column letters

The DB stores entities (`attendance_days` container + `visits` / `work_segments` / `travel_legs`), not sheet rows. `rowData` (keys are the spreadsheet column letters `C` … `AO`) is a projection that exists only in `packages/core/src/domain/attendance/sheetLayout.ts`: `projectDay(sheet)` → full 25-column `rowData` + `changedFields` + `hiddenVisitCount` (visits `seq` 1–3 fill the sheet slots; 4+ are stored but not shown, with a WARN), and `applyRowEdit(sheet, patch, { source })` → validated entity changes (times `HH:mm`, distances 2 decimals, `overridden_fields` for user edits; overlapping visits are allowed, as in GAS; overrides of an entity that disappears are parked on the day as `visit:<seq>:<field>` and handed to the next entity in that slot, like GAS cell backgrounds). `source` is `user` | `calendar_sync` | `import` (the `import:attendance` script for existing 出勤簿 CSVs). The UI-side mapping is `packages/web/src/features/attendance/model/dayRecord.ts`. Everything else uses the named definitions (`VISIT_SLOTS`, `MOVE_LEGS`, `SLOT_DEFS`…); don't write column letters anywhere else (the one other place is `sheetTemplate.ts`, below), and keep `gasParity.test.ts` green. Writes are diffs (delete → update → insert) with `entity_changes.before` (jsonb) holding before-values. Month lock: only the current month (tenant timezone) is editable (`monthLock.ts`); calendar sync is exempt, as in GAS; `attendance_periods.status='locked'` is enforced by a DB trigger (`KH001`, ordered against concurrent locking by per-period advisory locks); the app can only lock (unlock/delete is refused; operators use `platform.unlock_attendance_period()`). Locked `care_records` refuse any change/delete (`KH002`). Tenants are deleted only by `platform.purge_tenant()` (terminated tenants; the triggers let the cascade through when the tenant row is gone).

### Attendance Excel export (replaces the per-staff 出勤簿 spreadsheets)

`GET /api/attendance/export?month=|fiscalYear=&staffId?` (one staff: 1 sheet, or 12 sheets April–March named like GAS's `<スタッフ名>_出勤簿_<年度>年度`; staff get themselves, coordinator/admin via `targetStaffIdOf`) and admin-only `GET /api/attendance/export/all?month=` (every staff active on the 1st of the month, one sheet each, ≤ `MAX_ATTENDANCE_EXPORT_STAFF` = 100, one bulk build at a time per instance). Data comes from `loadAttendanceMonth` (the same loader as `GET /month`, so values match 今月のまとめ) plus receipt details (`core/usecases/attendance/export.ts`). The sheet columns/headers/**formulas** are the customer's 出勤簿テンプレート (`core/domain/attendance/sheetTemplate.ts`: inputs are written as values with times as Excel time serials, derived columns are the template's Excel formulas, plus AP 働いた時間 and AQ per-day receipts via `SUMIFS`; the workbook sets `fullCalcOnLoad`); layout/styling is `api/src/export/attendanceWorkbook.ts` (`exceljs`, buffered, bounded). `attendanceWorkbook.test.ts` evaluates the written formulas with `testFormulaEvaluator.ts` and compares with the domain values; `attendanceWorkbook.libreoffice.test.ts` does the same with real LibreOffice when `soffice` exists (skipped otherwise). If you change `attendanceCalc.ts` or the template, keep both in sync. Rate limit `attendance_export_staff`; INFO `attendance.export.downloaded` / SECURITY `attendance.export_all.downloaded`. The web downloads via `api.download()` + `saveBlobAsFile` (errors become normal API errors/toasts). Spec: doc/02 §8.6.

### Schedule / route provider

`SCHEDULE_PROVIDER` = `google` (Calendar API + Geocoding/Routes API, `integrations/src/google-schedule`) | `gas_bridge` (delegate to the GAS Web App; only for the `GAS_BRIDGE_TENANT` tenant — `GasBridgeTenantGuard` refuses other tenants before calling the Bridge, and there is no Bridge `MapsPort`, so staff home addresses aren't geocoded in that mode) | `noop` (always empty). If unset it is inferred from credentials (`integrations/src/schedule-provider/scheduleProvider.ts`); production requires it explicitly. Screen reads may use the 2-hour in-process route cache; **anything written to official records (calendar→attendance sync, nightly job) must use `getFreshScheduleWithRouteForStaff` / `{ fresh: true }`**, which neither reads nor writes the cache and fails (502) instead of returning partial data when a calendar can't be read. All tenants' calendars are read with one platform Google identity, so which calendars a tenant may read is **operator data**, not tenant-admin data: `platform.tenants.calendar_settings` (`sharedCalendars` + `allowedStaffCalendars` = exact ids or `@domain` suffixes, generic domains like `@gmail.com` / `@group.calendar.google.com` only as exact ids; `core/domain/schedule/calendarPolicy.ts`), written only by `pnpm tenant:calendars` over `MIGRATION_DATABASE_URL` (the app role can only SELECT `platform.*`). Staff calendar ids are checked on admin save and again at read time (`resolveCalendarSources`, busy-block sync). Details: `doc/05_バッチ・外部連携.md` §4.

### External customer ingest API

`POST /api/integrations/customers` (contract `shared/src/contracts/integrations.ts`, ≤500 customers, 2MB body limit in `apiBodyLimits`, rate limit `integration_customers_key` per key) maps each item (the customer's full current state; omitted = cleared) onto `CustomerSnapshot` (`ingestion/src/integrationCustomers/`) and applies all of them in one UoW with `applyCustomerSnapshot` + an `import_runs` row (`source = external_api`), bumping the customer data version when something changed. Upsert only — archiving customers that disappeared stays with the full CSV import. Each key is bound to one `CUSTOMER_SOURCES` value: `reserva` (same RESERVA ids as the CSV; the only source schedule matching uses) or `external_api` (a separate id space). Docs: doc/04 2.11, doc/05 11, doc/06 4.2.

### Admin tab (🛠 管理)

`packages/web/src/features/admin` (lazy-loaded tab, admins and coordinators; coordinators see only 報告一覧): スタッフ (`core/usecases/staffAdmin.ts`: list/create/update with `rowVersion` → 409 on conflict, retire (sets `retired_on`; sessions are revoked when the date is today or earlier), delete only when the staff has no business records (FK references plus the FK-less history columns), no self role change/retire/delete, changes that remove an admin lock the active admin rows and are refused if no admin without a retirement date would remain (`last_admin`), home address geocoded on save via `MapsPort` — stored address-only when geocoding fails; schedule calendar id = `staff_calendars` purpose `schedule`, accepted only if it matches the tenant's operator-managed allowlist; password-guide mail reuses the reset-code flow and its rate limit), AIプロンプト (`core/usecases/aiPrompts.ts`: per-key `revision`, a stale revision is 409 and nothing is written; body `null` = back to default; history in `ai_prompt_revisions`), 操作ログ (`core/usecases/auditLogs.ts`: tenant-only `app_logs`, filters by period (≤93 days) / level / staff / action, keyset paging, BOM UTF-8 CSV; viewing and downloading are logged), 報告一覧 (`core/usecases/reportList.ts`, admins + coordinators: everyone's `care_records` filtered by period (≤366 days, default 31) / kind / author / customer, keyset paging on `(occurred_at DESC, id DESC)`, read-only detail with revision count, CSV via `GET /api/reports/export.csv?sheet=daily|accident` in the mirror sheets' column order (`routes/reportCsv.ts`; streaming/abort/failure marker shared with the audit CSV in `http/csv.ts` `writeCsvStream`); list pages including others' records, others' detail and exports are logged). Spec: doc/02 §10, API: doc/04.

### Web Push (next-day schedule notice)

`features/notifications` (settings 通知 toggle per device + test notice) → `POST/DELETE /api/push/subscriptions` (`push_subscriptions`, owned by the logged-in staff; `core/usecases/pushNotifications.ts`). Re-subscribing an endpoint that belongs to another staff moves it to the current one; max 10 subscriptions per staff (`MAX_PUSH_SUBSCRIPTIONS_PER_STAFF`, the least recently used are trimmed); subscribing is rate-limited to 30/h per staff (`push_subscribe_staff`). Device hand-over: logout (`useSession().logout` → `stopPushOnThisDevice`) drops this device's subscription (server row + browser) if this user turned it on here; login (`releaseForeignPushSubscription`) unsubscribes a browser subscription someone else turned on (their server row stays until the push service reports it gone); retirement with `retired_on` today or earlier (`staffAdmin.ts`) deletes all the staff's subscriptions with the sessions. The `route-notice` job (19:00 JST) reads, for each active staff with a subscription, the target date's light schedule in strict mode (no Maps calls; an unreadable calendar fails that staff instead of sending a partial list) and, if there are events, enqueues one `push.route_notice` **per subscription** (dedupe `push.route_notice:<subscriptionId>:<staffId>:<date>`, so re-runs add only newly subscribed devices) with an `expiresAt` (a 「明日の予定」 notice expires when that day starts, a re-sent other-date notice when that day ends; TTL = time left, max 24h). The payload is only times + customer display names (no address/phone/route). The worker sends via `integrations/src/web-push` (`sendPushNotice`): expired, deleted or re-assigned subscriptions are skipped; 404/410 deletes the subscription; other 4xx count as rejections (no retry; deleted after 3 in a row); 5xx/429/network errors throw so the outbox retries only that device. Tapping opens `/?schedule=YYYY-MM-DD` on the schedule tab. iOS needs the PWA added to the home screen (16.4+). Details: doc/05 §10.

### Outbox (mirror to GAS sheets, mail, Web Push)

PostgreSQL is the source of truth. Writes that GAS-side sheets still need enqueue an `outbox_messages` row **in the same Unit of Work** as the domain write, with a deterministic `dedupe_key` `<topic>:<aggregateId>:<version>` (`core/domain/outbox/dedupeKey.ts`; re-enqueueing the same key is a no-op; the attendance aggregate uses a per-day sequence in the payload, compared against `OutboxWriter.latestPayload`; the attendance-day payload carries the changed `columns`, and only those are sent). Topics (`core/domain/model/codes.ts` `OUTBOX_TOPICS`): `mirror.attendance_day`, `mirror.attendance_aggregate`, `mirror.care_record`, `mirror.receipt`, `mail.password_reset` (also the admin password-guide mail), `push.route_notice`, `push.test`. Mirror/mail payloads carry IDs only; `push.*` payloads carry the notice text. The GAS Bridge (`GAS_BRIDGE_URL` + `GAS_BRIDGE_SECRET` + `GAS_BRIDGE_TENANT`, all three or none — `gas-bridge/gasBridgeEnv.ts` fails startup otherwise; `MIRROR_TO_GOOGLE_SHEETS=true` requires them) belongs to exactly one tenant: mirror topics are enqueued/sent only for the `GAS_BRIDGE_TENANT` slug. The UoW's `outboxPolicy` (`outboxTopicPolicyOf(env)` → `core/domain/outbox/topicPolicy.ts` `isOutboxTopicEnabled`; mirror checks read the UoW tenant's slug) skips mirror topics for other tenants or when the mirror is off, and `push.*` without `VAPID_PUBLIC_KEY`; the worker applies the same policy and completes leftover ones without sending (a mirror message of another tenant also logs WARN `outbox.mirror_other_tenant_skipped`) — both read the same shared env. A `DrizzleUnitOfWork` without `outboxPolicy` enqueues everything (DB integration tests only). The mirror is one-way: nothing flows back from the sheets, and the staff master sheet is never written. The worker (`core/usecases/outboxWorker.ts`) claims one message at a time across tenants with `FOR UPDATE SKIP LOCKED` and a lease (`locked_until`; results are written only while the lease — `locked_by` + `attempts` — is still ours, and expired leases at `max_attempts` go `dead`), processes it outside the transaction, re-reads the record, and posts to the GAS `Bridge.js` actions (`integrations/src/gas-bridge/gasBridgeMirrorSenderPort.ts`; without `GAS_BRIDGE_URL` sending is a no-op). Failures back off exponentially (`core/domain/outbox/retryPolicy.ts`) up to the message's `max_attempts` → `dead` (+ ERROR `outbox.message_failed`); `PermanentOutboxError` → `failed`. The Bridge write actions exist in GAS `Bridge.js` Ver. 1.1.38+ (older versions mis-order accident columns and duplicate receipts); payloads and the query-string-secret limitation are in `doc/05_バッチ・外部連携.md` §9.

### Worker jobs

`packages/worker/src/entrypoints/`: `routeNotice.ts` (replaces `gas-root-serach`'s nightly `main()` LINE WORKS DM, 19:00 JST, `var.route_notice_schedule`; tomorrow in each tenant's timezone; optional date to re-send), `nightlyCalendarSync.ts` (GAS `autoSyncTodayScheduleForAllStaff`, 22:00 JST; each tenant's "today" in its timezone, staff active on that date), `csvImport.ts` (GAS `checkAndImportLatestCsv`, 03:00 JST; the tenant's Drive folder from `platform.tenants.customer_import_settings` (operator CLI `pnpm tenant:customer-source`, zod `tenantCustomerImportSettingsSchema` in shared, read via `r.customerImportSettings()`), else local `CUSTOMER_CSV_LOCAL_DIR/<slug>/Kokyaku_*.csv` for dev, else `not_configured`; refuses to apply if >20% of customers would disappear → `review_required`), `maintenance.ts` (04:00 JST, all non-purged tenants: app_logs partitions 12 months ahead + moving rows out of `app_logs_default`, retention deletes, unreferenced stored files — `core/usecases/maintenance.ts` `RETENTION_DAYS`), `syncBusyBlocks.ts` (free/busy for future matching), `outboxOnce.ts`. Jobs are idempotent, exit 1 on any failure, on `JOB_TIMEOUT_MS`, or when stopped before finishing (Cloud Run Jobs retry), stop at the next checkpoint on SIGTERM (`jobs/stopSignal.ts`, forced exit after `WORKER_SHUTDOWN_TIMEOUT_MS`) and close the DB pool; and are scheduled by Cloud Scheduler in production (`infra/gcp/scheduler.tf`); `WORKER_IN_PROCESS_CRON=true` runs them inside the poller locally. The GAS triggers they replace must be disabled on cut-over day (`doc/09_移行計画.md`); `gas-root-serach`'s `main()` is removed only after every staff member has turned notifications on.

### Migrations

- The baseline is `0000_baseline.sql` (drizzle-kit output; only the header with `btree_gist` and `app_current_tenant()` is hand-added) and `0001_baseline_custom.sql` (hand-written: `set_updated_at` triggers, EXCLUDE constraints, `ON DELETE SET NULL (col)`, the attendance lock / period guard and care-record guard triggers, partitioned `app_logs` with a default partition + partition functions, `platform.provision_tenant()` / `purge_tenant()` / `unlock_attendance_period()`, FORCE RLS, per-role GRANTs). `app_logs` is defined outside the drizzle-kit schema (`src/customTables/`).
- Edit `packages/db/src/schema/*.ts`, then `pnpm db:generate` to create the next migration; commit schema + SQL + `drizzle/meta`, and regenerate the table reference with `pnpm db:migrate && pnpm db:doc`. `pnpm db:generate` must report "No schema changes" when you're done (CI checks).
- Things drizzle-kit can't express (EXCLUDE, triggers, FORCE RLS and GRANTs for new tables) go in a new hand-written migration (`pnpm --filter @katahimo/db exec drizzle-kit generate --custom --name <name>`).
- **Never edit an applied migration** once there is production data. Migrations run before the new app version deploys, so keep them backward compatible (add column → deploy → drop old column next release).
- `packages/db/src/migrate.ts` requires `MIGRATION_DATABASE_URL` and refuses to run unless the session role is `katahimo_owner`.

## Verification (GAS logic parity + e2e)

GAS is the spec for business logic and calculation results only; screens are verified on their own by the e2e journey and the web tests.

- **Logic parity tests** run the legacy GAS source itself in `node:vm` with fake GAS services and compare outputs with the TypeScript port: `packages/core/src/domain/attendance/gasParity.test.ts` (seeded random inputs through `testSupport/gasLegacy.ts`) and `packages/integrations/src/google-schedule/gasParity.test.ts` (`RouteSearch.js` scenarios). When porting more GAS logic, add a parity test in the same style rather than eyeballing.
- **Live journey (e2e)**: `pnpm e2e` (= `pnpm --filter @katahimo/e2e e2e`; seeded DB; starts the API and Vite if they aren't running) drives, as the admin, login → schedule → customers → report/receipts → attendance (incl. saving the month / all-staff Excel) → settings (text size, admin details, the 通知 section hidden without VAPID) → the 🛠 管理 tab (staff add/list/edit/delete, delete refused for a staff with records; AI prompt edit/reload/reset to default; audit-log list and CSV; report list, detail and CSV) → logout, then a non-admin checks that the 🛠 管理 tab and other admin UI are hidden and admin/coordinator APIs (incl. the report CSV and `GET /api/attendance/export/all`) return 403. The e2e browser gets `LANG=C.UTF-8` when unset (otherwise headless Chromium drops Japanese download file names). Screenshots per step in `tools/e2e/out/e2e/` (gitignored). It writes to the DB — dev only. `--web-url` reuses a running server, `--only '<regex>'` narrows to matching steps. Sending Web Push (subscribe, test notice, route notice) is not in the journey (the e2e env has no VAPID keys); it is covered by `features/notifications/*.test.ts(x)`, `core/usecases/pushNotifications.test.ts` and the Web Push block of `packages/api/src/routes.integration.test.ts`; the admin API is also covered by `packages/api/src/admin.integration.test.ts`, the report list/detail/CSV API by `packages/api/src/reports.integration.test.ts`.
- Chromium is preinstalled at `/opt/pw-browsers` and `playwright-core` is pinned to 1.56 to match; never run `playwright install`.

## Porting rules

- **Submodule**: `legacy/gas-childcare-visit-app` is read-only. Never edit it here; fixes go to `katahimo-dev/gas-childcare-visit-app`, then `git submodule update --remote legacy/gas-childcare-visit-app` and commit the pointer bump. The GAS app source is in `legacy/gas-childcare-visit-app/gas-childcare-visit-app/`; its `CLAUDE.md` has the file map and caching layers.
- **Clean code over GAS-isms**: reproduce GAS *behavior* (outputs, validation messages, edge cases), not its *implementation*. No `innerHTML` string building (JSX), no identity by staff/customer name or sheet row number (use IDs), no column letters outside the layout layer, no client-trusted identity, no whole-sheet rewrites (diff-apply), no hidden global state. Put logic in pure `core/domain` functions with tests, I/O behind ports. When GAS has a bug, fix it and document the deliberate difference (`doc/02_機能仕様.md` §11 / `packages/web/README.md`, and the verdict row in `doc/11_GAS版との機能比較.md`) instead of copying it.
- UI work follows `packages/web/README.md` (GAS class names verbatim, Tailwind v3 default theme, `FadeModal`, `showToast`, `STORAGE_KEYS` for every localStorage key, `AdminTargetStaffSelect` + `requestStaffId` for admin targeting, TanStack Query keys under `queryKeys.customers.all` for customer data).
- Secrets only via env / Secret Manager. Web Push's VAPID private key is the Secret Manager secret `vapid-private-key` (worker only; public key + subject in `var.web_push`). Production (`NODE_ENV=production`) refuses to start without `SECRET_BOX_PROVIDER=gcp` (API), `STORAGE_PROVIDER=gcs`, explicit `SCHEDULE_PROVIDER`, a 32+ char `SESSION_SECRET` (API), and `SMTP_HOST` (worker — password-reset mail is enqueued to the outbox by the API and sent by the worker, so the outbox poller must run in production).
- Record user-visible or operational changes in `CHANGELOG.md` (`## [Ver. x.y.z] - date`, Japanese).
