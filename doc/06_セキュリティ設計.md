# 06. セキュリティ設計

- 目的: 何から何を守るか(脅威)と、その対策をコードの場所と一緒に決める。受け入れているリスクと未対応の項目も明記する。
- 対象読者: 開発者(変更のときに守る約束)、セキュリティレビューをする人、運用者。

扱うデータ: 子どもと保護者の氏名・住所・電話・生年月日・アレルギー・配慮事項・緊急連絡先、保育の記録(日報・事故報告)、
スタッフの勤怠・位置(自宅)・認証情報、領収書の画像。要配慮の個人情報を含むため、**漏えい・取り違え(別の法人・別の人)・改ざん**
を主な脅威とする。

## 1. 脅威と対策の一覧

| 脅威 | 対策 | 場所 |
| --- | --- | --- |
| 別の法人のデータが見える・書ける | テナントIDはセッションからだけ決める、FORCE RLS、複合外部キー、`app_current_tenant()` が NULL なら何も見えない | 3章・[03](03_データベース設計.md) 4章 |
| 一般スタッフが他人のデータを扱う | 対象スタッフはサーバーが決める(`targetStaffIdOf`)、usecase でも確かめる、他人の報告の上書きは 403 | 4章 |
| なりすまし・総当たり | argon2id、照合前の回数制限、アカウント・IP の一時ロック、応答時間をそろえる | 2章・[04](04_API仕様.md) 1.5 |
| セッションの盗用 | httpOnly・SameSite=Lax・`__Host-` の Cookie、DB はトークンのハッシュだけ、無操作7日・最長30日、退職・再設定・パスワード変更で失効 | 2.2 |
| CSRF・クリックジャッキング・XSS | `Sec-Fetch-Site` / `Origin` の確認、JSON 以外の本体を拒否、CSP(スクリプトは同一オリジンのファイルだけ)、`frame-ancestors 'none'`、JSX(innerHTML を使わない) | 5章 |
| 大きな要求・サービス妨害 | 本体の上限、画像の枚数と大きさ、パスワードの最大長、DB の文・ロック・放置の上限、従量課金の API の回数制限 | 6章 |
| SSRF(通知先に内部のURL) | Webhook は Google Chat の URL だけ、リダイレクトを追わない、10秒で打ち切る | 7章 |
| DB・バックアップの漏えい | 要配慮の列の暗号化(テナントごとの DEK を KMS の KEK で包む)、ブラインドインデックスは HMAC | 8章 |
| 秘密値の漏えい | Secret Manager・`.env`(コミットしない)、画面には伏せ字だけ、ログに値を出さない | 9章 |
| 記録の改ざん・消失 | 確定済みの記録・締めた月はトリガーが拒否、本文の変更前を履歴に、出勤簿の変更前を `entity_changes` に、操作ログは追記専用 | 10章 |
| 権限の大きすぎる DB ユーザー | 用途ごとのロール、テーブルごとの GRANT、SUPERUSER・BYPASSRLS なし | [03](03_データベース設計.md) 5章 |

## 2. 認証

### 2.1 パスワード

- ハッシュは argon2id(`@node-rs/argon2` の既定のパラメータ。`api/src/authAdapters.ts` の `argon2PasswordHasher`)。
- GAS版のハッシュ(`sha256(password + AUTH_SALT)`、全スタッフ共通のソルト)はスタッフ台帳の取込で `legacy_password_hash` に移し、
  初回ログインで照合できたら argon2id に作り直す(`domain/legacyAuth/computeLegacyHash.ts`・`usecases/auth/login.ts`)。照合は
  長さを揃えた定数時間の比較。`LEGACY_AUTH_SALT` は移行が終われば不要。
- パスワードの長さは8〜128文字(`defaults/passwordPolicy.ts`。上限は argon2 への過大な入力を防ぐ)。
- 存在しないテナント・アカウント・パスワード未設定のスタッフでも、ダミーの argon2 照合をして応答時間をそろえる(`verifyDummy`)。
- ログインIDはメールとサブメール(`staff_login_emails`、正規化して小文字)。テナントは slug で先に決め、そのテナントの RLS の
  中でスタッフを探す(全テナントを横断してメールを探さない)。
- 回数制限: 照合の前に枠を取る(アカウント 15分に10回、IP 15分に50回 → 15分ロック)。ロックの開始・ロック中の試行は SECURITY ログ。

### 2.2 セッション

| 項目 | 内容 |
| --- | --- |
| トークン | 乱数の生トークンを Cookie にだけ持ち、DB は SHA-256(`sessions.token_hash`)だけ。Cookie の値は `テナントID.生トークン`(テナント部分は書き換えられうるため、セッションが見つかるまではテナント不明として扱う) |
| Cookie | `HttpOnly`・`SameSite=Lax`・本番は `Secure` と `__Host-` 接頭辞(サブドメインから上書き・注入できない) |
| 期限 | 無操作7日(残り6日を切ると延長)、ログインから30日(`usecases/auth/session.ts`) |
| 毎回の確認 | 失効・期限・テナントの状態(`active` 以外は拒否。停止中はセッションを残し、再開すれば使える)・スタッフ・退職日 |
| 失効 | ログアウト(その1本)、パスワード変更(操作中以外の全て)、再設定の完了・退職日の設定・退職日の到来(全て) |

### 2.3 パスワード再設定

- コードは6桁の数字(GAS版と同じ。入力しやすさを優先し、桁数ではなく回数で守る)、有効期限30分、1回限り、新しいコードを出すと古いものは無効。
- DB は `HMAC-SHA256(鍵, staffId:code)` だけを持つ。鍵は `SESSION_SECRET` から HKDF(`katahimo/password-reset-code/v1`)で導出した
  専用の値。DB が漏れてもこの鍵が無ければコードを逆算できない。
- 1つのコードへの入力は5回まで。試行回数の加算と上限の判定を照合より前に1文の条件付き UPDATE で行い、使用済みへの遷移も
  1行を得たときだけ成功にする(並列に送っても上限を超えて試せず、同じコードで2回再設定できない。結合テストで確かめる)。
- 発行の要求はアカウントの有無・送信の成否にかかわらず同じ応答。アカウント単位の上限を超えた要求は既存のコードに触れない
  (第三者が有効なコードを無効にし続けられない)。
- メールはワーカーが送る。API は送信待ちのコードを暗号化して保存し outbox に積むだけ(SMTP の所要時間が応答時間に出ない。
  Cloud Run の API は応答後に CPU が絞られるため)。送信後・使用後・期限切れで送信待ちのコードを消す。
- 送信先は台帳の値だけ(サブメールで要求したらサブメール宛)。

## 3. テナント分離

- テナントIDは**セッション Cookie からだけ**決まる(`getAuthenticatedSession`)。要求の本体・クエリの `tenantId` は使わない。
- DB は FORCE RLS(所有者にも)と複合外部キーで二重に守る。Unit of Work がトランザクションの中だけ `app.tenant_id` を設定し、
  リポジトリはテナントIDを受け取らない。
- テナントの作成は `platform.provision_tenant()`、消去は `platform.purge_tenant()`(解約済みだけ)。どちらも所有者のメンバー
  (`katahimo_migrator`)だけが実行できる SECURITY DEFINER。アプリ・ワーカーは `platform.tenants` を読むだけ。
- ワーカーだけがテナントを横断して outbox を取り出せる(`outbox_messages_worker` ポリシー)。処理はそのメッセージのテナントの
  Unit of Work で行う。
- 結合テスト(`tenancy.integration.test.ts`・`catalog.integration.test.ts`)がテナントの分離と約束の書き忘れを確かめる。

## 4. 認可(admin-vs-self)

GAS版の規則「クライアントが送ったスタッフ名を信用しない」をスタッフIDで引き継ぐ。

| 仕組み | 内容 |
| --- | --- |
| 役割 | `staff` / `coordinator` / `admin`(`shared/src/contracts/roles.ts` の `isAdminRole`・`canActForOthers`) |
| ミドルウェア | `requireSession(container, deniedAction?)`・`requireAdmin(container, action)`(401 / 403 と WARN `<action>.access_denied`)。`actorOf(c)` が usecase の `Actor` |
| 対象スタッフ | `targetStaffIdOf(c, 要求のstaffId)` → `resolveTargetStaffId`: 一般スタッフは常に本人。usecase も確かめる(`loadAttendanceTarget` 等は forbidden を投げる) |
| 報告の上書き | 一般スタッフは本人の報告だけ(403、SECURITY `report.*.save_denied`)。顧客・担当の違う上書きは 409(`customer_mismatch` / `author_mismatch`) |
| 管理者だけ | `/api/admin/*`・`/api/settings/admin/*`・`POST /api/attendance/day/aggregate/refresh` |
| 画面 | 出し分けは見た目だけ。本当の判定はサーバー(e2e で一般スタッフの 403 と、他人の `staffId` を送っても本人になることを確かめる) |

閲覧できるお客様は GAS版と同じく全スタッフが全顧客(担当だけに絞るかは運用で決める未決事項)。詳細を開いた記録を INFO
`customer.detail.viewed` に残す。

## 5. ブラウザまわり(`api/src/http/security.ts`)

- **CSRF**: 状態を変える `/api/*` の要求は `Sec-Fetch-Site` が `same-origin` / `none` 以外なら 403、無ければ `Origin` のホストが
  `Host` と違えば 403。どちらも無い要求(ブラウザ以外)は通す(Cookie を勝手に送られる前提に当たらない)。`SameSite=Lax` と合わせた多層防御。
- **Content-Type**: 本体のある状態変更は `application/json` だけ(415)。フォーム送信(事前確認なしで別サイトから送れる形式)を受けない。
- **CSP**: `default-src 'self'`、`script-src 'self'`(インラインのスクリプト無し。PWA の登録も外部ファイル)、`style-src 'self'
  https://fonts.googleapis.com`、`style-src-attr 'unsafe-inline'`(style 属性だけ)、`font-src 'self' https://fonts.gstatic.com`、
  `img-src 'self' data: blob:`(領収書のプレビュー)、`connect-src 'self'`、`object-src 'none'`、`base-uri 'self'`、`form-action 'self'`、
  `frame-ancestors 'none'`。ビルド済みの画面をこの CSP で読み込み、違反が出ないことを確かめている。
- **その他のヘッダー**: `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`、
  COOP / CORP `same-origin`、`Permissions-Policy`(カメラ・マイクは自分だけ、位置・支払いは無し)、本番だけ HSTS(1年・サブドメイン)。
  `/api/*` は `Cache-Control: no-store`。
- **画面**: JSX で描く(GAS版の innerHTML の組み立てはしない)。localStorage には個人情報を含む値をその人のキーだけに置き、
  ログアウトで消す(`packages/web/README.md`)。

## 6. 入力の上限と資源の保護

| 対象 | 上限 |
| --- | --- |
| 要求の本体 | 既定 256KB、領収書の登録 14MB、OCR 3MB(413) |
| 領収書の画像 | 1回6枚、1枚1.5MB(復号後)、JPEG / PNG / WebP を中身の先頭バイトで判定。1枚でも不正なら何も保存しない |
| テキスト | AI に渡すメモ 20,000字、APIキー 500字、Webhook URL 2,000字、モデル名 200字 等(契約の `max`) |
| パスワード | 128文字 |
| DB | ロールごとの `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout`(アプリ 15s / 5s / 30s、ワーカー 60s / 10s / 60s) |
| 従量課金 | AI 生成 1日200回、OCR 1日300回、ルートの再計算 1時間30回(スタッフごと) |
| ジョブ | `JOB_TIMEOUT_MS`(既定30分) |

大量の要求そのものは Cloud Run に届く(Cloud Armor は未導入。11章)。

## 7. 外部への送信(SSRF など)

- Google Chat の Webhook: 保存時と送信時に `https://chat.googleapis.com/v1/spaces/<space>/messages?…` の形だけを許す
  (`domain/notifications/googleChatWebhook.ts`)。リダイレクトは追わず、10秒で打ち切り、失敗の記録に応答本文を残さない。
- Gemini のキーはヘッダー(`x-goog-api-key`)で送る。GAS Bridge のシークレットはクエリにも載る(受け入れているリスク。11章)。
- 送信元IP(ログ・回数制限)は `X-Forwarded-For` の右から `TRUSTED_PROXY_HOPS` 番目(Cloud Run 直は1、外部ロードバランサを前に
  置くなら2、0 なら接続元)。利用者が偽装した値は左側に並ぶため使わない。

## 8. 暗号化と鍵

詳細は [03_データベース設計.md](03_データベース設計.md) 8章。

| 鍵 | 置き場所 | 用途 | 変えると |
| --- | --- | --- | --- |
| KEK(Cloud KMS `tenant-kek`) | Cloud KMS(90日ごとに自動ローテーション) | DEK のラップ | 旧版も有効なまま残るので読める。旧版を無効化・破棄するには全テナントの DEK の再ラップが必要(**処理は未実装**) |
| `LOCAL_DEV_KEK` | `.env`(開発だけ) | 同上 | 既存の DEK が読めなくなる |
| DEK(テナントごと・版ごと) | `tenant_data_keys`(ラップ済み) | 列の AES-256-GCM | 新しい版を `active` にし古い版を `decrypt_only` にすれば読める。**版を足す・再暗号化する処理は未実装**(形式・読み書きは複数の版に対応済み)。`destroyed` にすると暗号学的に削除 |
| `BLIND_INDEX_MASTER_KEY` | Secret Manager `katahimo-blind-index-key` | 領収書の重複判定の HMAC | 既存のインデックスが引けなくなる(値の先頭の鍵の版を上げ、再計算の処理で移す。未実装) |
| `SESSION_SECRET` | Secret Manager `katahimo-session-secret` | 再設定コードの HMAC・回数制限のキーの導出(HKDF で用途ごと) | 送信待ちの再設定コードが使えなくなり、回数制限の数え直しになる(セッションは DB の行なので切れない) |

`KMS_PROVIDER` は環境ごとに最初に決めて変えない(`kek_key_name` で取り違えを検出する)。本番は `KMS_PROVIDER=gcp` でなければ起動しない。

## 9. 秘密値の管理

- ソースに書かない。ローカルは `.env`(`.gitignore` 済み。`.env.example` に項目と説明)、本番は Secret Manager から Cloud Run の
  環境変数に入れる。サービスアカウントは自分の使う secret だけを読める(`infra/gcp/secrets.tf`)。
- テナントごとの秘密値(Gemini のキー・Chat の Webhook URL)は `tenant_secrets` に暗号化して置き、画面には伏せ字と設定済みの印だけを返す
  (`SECRET_MASK_CHAR`)。伏せ字のまま保存しても値は変わらず、伏せ字の一部だけ書き換えた値は拒否する。
- 本番の起動時の検証(`NODE_ENV=production`): `KMS_PROVIDER=gcp` + `GCP_KMS_KEY_NAME`、`STORAGE_PROVIDER=gcs` + `GCS_BUCKET`、
  `SCHEDULE_PROVIDER` の明示、(API)32文字以上の `SESSION_SECRET`、(ワーカー)`SMTP_HOST`。足りなければ起動前に落ちる。

## 10. 監査ログ・記録の保全

- 操作ログは `AppLogPort.write`(`app_logs`、月のパーティション、アプリ・ワーカーは追記だけ)。規則は GAS版 `logToBuffer` と同じ:
  WARN / ERROR / SECURITY と全ての書き込みは必ず残し、読み取りの成功はお金のかかるもの(地図)と、他のスタッフのデータを扱ったとき
  (`targetStaffId`)、要配慮情報の閲覧(`customer.detail.viewed`)だけ残す。ポートは例外を投げない。
- `details` には ID・件数・理由コードだけを入れる(個人情報・本文・秘密値は入れない)。ログインIDはマスクして残す。
- 復号の監査は操作ごとに1件(`DecryptSession` → `AuditLogPort.recordDecrypt`、Cloud Logging)。
- 1要求1行のプロセスログ(`http/requestLog.ts`)はパスとステータスだけ(クエリ・本文は残さない)。リクエストIDで app_logs と結び付く。
- 記録の保全: 確定済みの記録(`KH002`)・締めた月(`KH001`)はトリガーが拒否し、解除は運用者だけ。記録の本文の変更前は
  `care_record_revisions`、出勤簿の変更前は `entity_changes`(暗号化)に残る。

## 11. 受け入れているリスク・未対応

| 項目 | 状況 | 対応の案 |
| --- | --- | --- |
| GAS Bridge のシークレットが URL のクエリに載る | Apps Script の Web App がヘッダーを読めないため | Bridge.js が POST 本体でも認証するようにしてからクエリを外す(05 9章) |
| 全スタッフが全顧客を閲覧できる | GAS版と同じ運用 | 担当だけに絞るかは業務で決める。閲覧は監査ログに残す |
| Cloud Armor・WAF が無い | アプリ側の回数制限だけ | 外部 HTTPS ロードバランサ + Cloud Armor(`TRUSTED_PROXY_HOPS=2`)(07) |
| Cloud SQL がパブリック IP を持つ | 承認済みネットワーク無し・Auth Proxy 経由だけ・直接の TCP は TLS 必須 | プライベート IP + Direct VPC egress |
| KEK の旧版の破棄・DEK の追加・ブラインドインデックスの鍵の入れ替え | 形式は対応済み、処理が未実装 | 再ラップ・再暗号化のジョブを作る |
| 氏名・電話・住所の文字列は平文 | 検索・一覧・予定計算に使うため | RLS・権限・監査ログで守る。緯度経度は暗号化 |
| 6桁の再設定コード | 回数制限で守る | — |
| 領収書バケットは Google 管理の鍵 | 既定 | CMEK(`tenant-kek` とは別の鍵) |
| 開示・削除の請求・データの書き出し | 表だけ | 画面・処理を作る |
