# 06. セキュリティ設計

- 目的: 何から何を守るか(脅威)と、その対策をコードの場所と一緒に決める。受け入れているリスクと未対応の項目も明記する。
- 対象読者: 開発者(変更のときに守る約束)、セキュリティレビューをする人、運用者。

扱うデータ: 子どもと保護者の氏名・住所・電話・生年月日・アレルギー・配慮事項・緊急連絡先、保育の記録(日報・事故報告)、
スタッフの勤怠・位置(自宅)・認証情報、領収書の画像。要配慮の個人情報を含むため、**漏えい・取り違え(別の法人・別の人)・改ざん**
を主な脅威とする。

## 1. 脅威と対策の一覧

| 脅威 | 対策 | 場所 |
| --- | --- | --- |
| 別の法人のデータが見える・書ける | テナントIDはセッションからだけ決める、FORCE RLS、複合外部キー、`app_current_tenant()` が NULL なら何も見えない | 3章・[03](03_データベース設計.md) 4章 |
| 別の法人のカレンダーの予定を読む(全テナントを1つの Google の ID で読むため、管理者がスタッフに他社のカレンダーIDを設定する) | 読めるカレンダーは運用担当者だけが決める(`platform.tenants.calendar_settings`、`pnpm tenant:calendars`。アプリの DB ユーザーは platform を読むだけ)。スタッフのカレンダーは許可の一覧(完全一致の ID・誰でも作れないドメインの後方一致)に合うものだけを保存でき(400 + WARN)、読むときにも確かめ直す | 4.1 |
| 別の法人の顧客CSVを取り込む・別の法人の記録を GAS版のスプレッドシートに書く(Drive のフォルダ・GAS Bridge は全テナント共通の資格情報で使うため) | 取込元のフォルダは運用担当者だけが決め(`platform.tenants.customer_import_settings`、`pnpm tenant:customer-source`)、1つのフォルダは1つのテナントだけ。GAS Bridge は持ち主のテナント(`GAS_BRIDGE_TENANT`)だけに使い、他のテナントのミラーは積まない・送らない、予定も求めない | 4.1 |
| 外部システム連携の API キーの盗用・なりすまし | キーは運用担当者だけが発行し、DB は SHA-256 だけ、テナントはキーから決める、取込元はキーに固定、削除はできない、失効できる、キーごとの回数制限、送信元IPごとの認証の失敗の一時ロック | 4.2 |
| 一般スタッフが他人のデータを扱う | 対象スタッフはサーバーが決める(`targetStaffIdOf`)、usecase でも確かめる、他人の報告の上書きは 403 | 4章 |
| なりすまし・総当たり | argon2id、照合前の回数制限、アカウント・IP の一時ロック、応答時間をそろえる | 2章・[04](04_API仕様.md) 1.5 |
| セッションの盗用 | httpOnly・SameSite=Lax・`__Host-` の Cookie、DB はトークンのハッシュだけ、無操作7日・最長30日、退職・再設定・パスワード変更で失効 | 2.2 |
| CSRF・クリックジャッキング・XSS | `Sec-Fetch-Site` / `Origin` の確認、JSON 以外の本体を拒否、CSP(スクリプトは同一オリジンのファイルだけ)、`frame-ancestors 'none'`、JSX(innerHTML を使わない) | 5章 |
| 大きな要求・サービス妨害 | 本体の上限、画像の枚数と大きさ、パスワードの最大長、DB の文・ロック・放置の上限、従量課金の API の回数制限 | 6章 |
| SSRF(通知先に内部のURL) | Webhook は Google Chat の URL だけ、リダイレクトを追わない、10秒で打ち切る。Web Push の送り先は既知のプッシュサービスの https だけ | 7章 |
| 通知からの漏えい(ロック画面・他人の端末) | 通知の中身は時刻とお名前だけ(住所・電話・URL なし)、端末の鍵で暗号化(RFC 8291)、購読は本人の端末だけ、ログアウトでやめる | 7.1 |
| DB・バックアップ・画像の保管場所からの漏えい | Cloud SQL(ディスク・バックアップ)と領収書バケットをこのアプリ専用の Cloud KMS の鍵で暗号化(CMEK)、鍵の権限を分ける | 8章 |
| アプリの権限を使った読み出し(侵害されたアカウント・コード) | RLS・最小権限・監査ログ・回数制限、画面の出し分けに頼らないサーバーの判定 | 3・4・8・10章 |
| 秘密値の漏えい | Secret Manager・`.env`(コミットしない)、画面には伏せ字だけ、ログに値を出さない。テナントの秘密値は SecretBox(8.3) | 8.3・9章 |
| 記録の改ざん・消失 | 確定済みの記録・締めた月はトリガーが拒否、本文の変更前を履歴に、出勤簿の変更前を `entity_changes` に、操作ログは追記専用 | 10章 |
| 権限の大きすぎる DB ユーザー | 用途ごとのロール、テーブルごとの GRANT、SUPERUSER・BYPASSRLS なし | [03](03_データベース設計.md) 5章 |

## 2. 認証

### 2.1 パスワード

- ハッシュは argon2id(`@node-rs/argon2` の既定のパラメータ。`api/src/authAdapters.ts` の `argon2PasswordHasher`)。
- GAS版のハッシュ(`sha256(password + AUTH_SALT)`、全スタッフ共通のソルト)はスタッフ台帳の取込で `legacy_password_hash` に移し、
  初回ログインで照合できたら argon2id に作り直す(`domain/legacyAuth/computeLegacyHash.ts`・`usecases/auth/login.ts`)。照合は
  長さを揃えた定数時間の比較。`LEGACY_AUTH_SALT` は移行が終われば不要。
- パスワードの長さは8〜128文字(`defaults/passwordPolicy.ts`。上限は argon2 への過大な入力を防ぐ)。
- 存在しないテナント・アカウント・パスワード未設定のスタッフでも、ダミーの argon2 照合をして応答時間をそろえる(`verifyDummy`)。
- ログインIDはメールとサブメール(`staff_login_emails`、正規化して小文字)。テナントは slug で先に決め、そのテナントの RLS の
  中でスタッフを探す(全テナントを横断してメールを探さない)。
- 回数制限: 照合の前に枠を取る(アカウント 15分に10回、IP 15分に50回 → 15分ロック)。ロックの開始・ロック中の試行は SECURITY ログ。

### 2.2 セッション

| 項目 | 内容 |
| --- | --- |
| トークン | 乱数の生トークンを Cookie にだけ持ち、DB は SHA-256(`sessions.token_hash`)だけ。Cookie の値は `テナントID.生トークン`(テナント部分は書き換えられうるため、セッションが見つかるまではテナント不明として扱う) |
| Cookie | `HttpOnly`・`SameSite=Lax`・本番は `Secure` と `__Host-` 接頭辞(サブドメインから上書き・注入できない) |
| 期限 | 無操作7日(残り6日を切ると延長)、ログインから30日(`usecases/auth/session.ts`) |
| 毎回の確認 | 失効・期限・テナントの状態(`active` 以外は拒否。停止中はセッションを残し、再開すれば使える)・スタッフ・退職日 |
| 失効 | ログアウト(その1本)、パスワード変更(操作中以外の全て)、再設定の完了・退職日の設定・退職日の到来(全て) |

### 2.3 パスワード再設定

- コードは6桁の数字(GAS版と同じ。入力しやすさを優先し、桁数ではなく回数で守る)、有効期限30分、1回限り、新しいコードを出すと古いものは無効。
- DB は `HMAC-SHA256(鍵, staffId:code)` だけを持つ。鍵は `SESSION_SECRET` から HKDF(`katahimo/password-reset-code/v1`)で導出した
  専用の値。DB が漏れてもこの鍵が無ければコードを逆算できない。
- 1つのコードへの入力は5回まで。試行回数の加算と上限の判定を照合より前に1文の条件付き UPDATE で行い、使用済みへの遷移も
  1行を得たときだけ成功にする(並列に送っても上限を超えて試せず、同じコードで2回再設定できない。結合テストで確かめる)。
- 発行の要求はアカウントの有無・送信の成否にかかわらず同じ応答。アカウント単位の上限を超えた要求は既存のコードに触れない
  (第三者が有効なコードを無効にし続けられない)。
- メールはワーカーが送る。API はメールに書くコードを送信待ちの間だけ `password_reset_codes.mail_code` に置き、outbox には
  コードの ID だけを積む(SMTP の所要時間が応答時間に出ない。Cloud Run の API は応答後に CPU が絞られるため)。送信後・使用後に
  この列を消し、送られないまま期限が切れた値は保守ジョブが消す(照合は `code_hash` だけで行う)。
- 送信先は台帳の値だけ(サブメールで要求したらサブメール宛)。

## 3. テナント分離

- テナントIDは**セッション Cookie からだけ**決まる(`getAuthenticatedSession`)。要求の本体・クエリの `tenantId` は使わない。
  例外は外部システム連携(`/api/integrations/*`)で、テナントは API キーから決まる(4.2)。
- DB は FORCE RLS(所有者にも)と複合外部キーで二重に守る。Unit of Work がトランザクションの中だけ `app.tenant_id` を設定し、
  リポジトリはテナントIDを受け取らない。
- テナントの作成は `platform.provision_tenant()`、消去は `platform.purge_tenant()`(解約済みだけ)。どちらも所有者のメンバー
  (`katahimo_migrator`)だけが実行できる SECURITY DEFINER。アプリ・ワーカーは `platform.tenants` を読むだけ。
- ワーカーだけがテナントを横断して outbox を取り出せる(`outbox_messages_worker` ポリシー)。処理はそのメッセージのテナントの
  Unit of Work で行う。
- 結合テスト(`tenancy.integration.test.ts`・`catalog.integration.test.ts`)がテナントの分離と約束の書き忘れを確かめる。

## 4. 認可(admin-vs-self)

GAS版の規則「クライアントが送ったスタッフ名を信用しない」をスタッフIDで引き継ぐ。

| 仕組み | 内容 |
| --- | --- |
| 役割 | `staff` / `coordinator` / `admin`(`shared/src/contracts/roles.ts` の `isAdminRole`・`canActForOthers`) |
| ミドルウェア | `requireSession(container, deniedAction?)`・`requireAdmin(container, action)`・`requireCoordinator(container, action)`(コーディネーター・管理者)(401 / 403 と WARN `<action>.access_denied`)。`actorOf(c)` が usecase の `Actor` |
| 対象スタッフ | `targetStaffIdOf(c, 要求のstaffId)` → `resolveTargetStaffId`: 一般スタッフは常に本人。usecase も確かめる(`loadAttendanceTarget` 等は forbidden を投げる) |
| 報告の上書き | 一般スタッフは本人の報告だけ(403、SECURITY `report.*.save_denied`)。顧客・担当の違う上書きは 409(`customer_mismatch` / `author_mismatch`) |
| 管理者だけ | `/api/admin/*`・`/api/settings/admin/*`・`POST /api/attendance/day/aggregate/refresh` |
| コーディネーター・管理者だけ | 全員分の日報・事故報告の CSV(`GET /api/reports/export.csv`)。一覧・中身(`GET /api/reports`・`/:id`)は一般スタッフには本人の記録だけ(一覧は `staffId` を無視、他人の中身は 403・SECURITY `report.detail.view_denied`) |
| 画面 | 出し分けは見た目だけ。本当の判定はサーバー(e2e で一般スタッフの 403 と、他人の `staffId` を送っても本人になることを確かめる) |

### 4.1 管理者の操作の守り

- **カレンダー**: 予定・free/busy は全テナント共通のサービスアカウントで読むため、どのカレンダーを読んでよいかはテナントの管理者の
  データにしない。共有カレンダーとスタッフのカレンダーの許可(完全一致の ID か `@ドメイン`)は `platform.tenants.calendar_settings` に
  置き、所有者の接続で動く運用担当者の CLI(`pnpm tenant:calendars`、SECURITY `tenant.calendar_settings.updated`)だけが変える。
  `@gmail.com`・`@googlemail.com`・`@group.calendar.google.com`・`@resource.calendar.google.com` 等の誰でも作れるドメインは後方一致に
  できない(ID を1つずつ登録する)。管理画面で合わないカレンダーを設定すると 400(`calendar_not_allowed`、WARN
  `staff.admin.*_rejected`)。許可を後から外したカレンダーは、予定・free/busy を読むときに飛ばす(WARN
  `calendar.staff_calendar_not_allowed`)。
- **顧客CSVの取込元**: Drive のフォルダも全テナント共通のサービスアカウントで読むため、どのフォルダを読むかは
  `platform.tenants.customer_import_settings` に置き、運用担当者の CLI(`pnpm tenant:customer-source`、SECURITY
  `tenant.customer_import_settings.updated`。フォルダID は残さない)だけが変える。環境変数でテナントとフォルダを対にする方式はやめた。
- **GAS Bridge(移行期)**: Bridge は1つのテナントの GAS版・スプレッドシートにつながっているため、持ち主のテナントの slug
  (`GAS_BRIDGE_TENANT`)を URL・シークレットと必ず一緒に設定する(揃っていなければ起動しない)。ミラーはそのテナントの記録だけを
  積み(UoW)、ワーカーも他のテナントの `mirror.*` を送らずに完了にする(WARN `outbox.mirror_other_tenant_skipped`)。
  `SCHEDULE_PROVIDER=gas_bridge` でも、他のテナントの予定は Bridge に求めない(スタッフ名で GAS版の予定を読ませない)。
- **管理者が残る**: 自分自身の役割の変更・退職・削除はできない。ほかの管理者を外す・退職させる・削除する操作は、在籍中の管理者の行を
  ロックしてから(FOR UPDATE)、操作する人がまだ管理者か(`actor_not_admin` 403)、退職日の決まっていない管理者が残るか
  (`last_admin` 409)を確かめる。同時に互いを外しても1人は残る。
- **退職**: 今日以前の退職日を入れるとそのスタッフのセッションを全て失効させる。先の日付ならその日からログインできなくなる。

### 4.2 外部システム連携の API キー

- 発行・一覧・失効は運用担当者の CLI(`pnpm tenant:api-keys`)だけ。所有者の接続で書き、アプリの DB ユーザーは
  `integration_api_keys` を読むことと `last_used_at` を書くことしかできない(列ごとの GRANT。管理画面・侵害されたアプリからキーを
  作れない)。発行・失効は SECURITY `tenant.api_key.created` / `.revoked`。
- トークンは `kth_<テナントID>_<32バイトの乱数(base64url)>`。`kth_` はシークレットのスキャンで見つけやすくするための目印。DB は
  トークン全体の SHA-256 だけを持ち(`token_hash`、テナント内で UNIQUE)、トークンは発行のときに1回だけ表示する。
- 認証は `Authorization: Bearer` だけ(Cookie は見ない)。トークンの `<テナントID>` で RLS のテナントを決めてからハッシュで
  引く(セッション Cookie と同じ考え方。テナントの部分を書き換えても、そのテナントに同じハッシュが無ければ 401)。平文を
  比べないため比べる時間からトークンを推し量れない。失敗は WARN `integration.auth_failed`(理由コードだけ。キーが見つかるまでは
  テナント不明として記録する)。
- 認証の失敗は送信元IPごとに数え(`integration_auth_failure_ip`: 15分に30回で15分ロック。ログインの `login_failure_ip` と同じく
  確かめる前に1回分を取り、成功した回は返す)、ロック中の要求は正しいキーでも DB で確かめずに 429 を返し、操作ログも残さない
  (誤ったキーの総当たり・壊れた連携先の送り続けで DB と操作ログが溢れないように)。ロックの始まりに1回だけ WARN `integration.auth_locked`。
- キーごとに書ける取込元(`reserva` / `external_api`)を固定し、要求の本体では選べない。受け取りは作成・更新だけで、削除・
  アーカイブはできない(キーが漏れても顧客を消せない。書き換えは `import_runs` と操作ログに残る)。
- 回数(キーごとに1時間120回)・1回500件・本体 2MB の上限(04 1.5・1.4)。
- 省いた項目は今の値のまま(null で空にする)。部分的な送信で住所・緊急連絡先・子どもを消さない(05 11章)。同じテナントの取込は
  テナントごとのアドバイザリロックで1つずつ適用し、再送が重なっても同じ顧客を2人作らない。適用に失敗したら全体を戻して
  ERROR `integration.customers.ingest_failed`(顧客の値は残さない)。

閲覧できるお客様は GAS版と同じく全スタッフが全顧客(担当のお客様だけに絞るのは次の段階。8.4)。詳細を開いた記録を INFO
`customer.detail.viewed` に残す。

## 5. ブラウザまわり(`api/src/http/security.ts`)

- **CSRF**: 状態を変える `/api/*` の要求は `Sec-Fetch-Site` が `same-origin` / `none` 以外なら 403、無ければ `Origin` のホストが
  `Host` と違えば 403。どちらも無い要求(ブラウザ以外)は通す(Cookie を勝手に送られる前提に当たらない)。`SameSite=Lax` と合わせた多層防御。
- **Content-Type**: 本体のある状態変更は `application/json` だけ(415)。フォーム送信(事前確認なしで別サイトから送れる形式)を受けない。
- **CSP**: `default-src 'self'`、`script-src 'self'`(インラインのスクリプト無し。PWA の登録も外部ファイル)、`style-src 'self'
  https://fonts.googleapis.com`、`style-src-attr 'unsafe-inline'`(style 属性だけ)、`font-src 'self' https://fonts.gstatic.com`、
  `img-src 'self' data: blob:`(領収書のプレビュー)、`connect-src 'self'`、`object-src 'none'`、`base-uri 'self'`、`form-action 'self'`、
  `frame-ancestors 'none'`。ビルド済みの画面をこの CSP で読み込み、違反が出ないことを確かめている。
- **その他のヘッダー**: `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`、
  COOP / CORP `same-origin`、`Permissions-Policy`(カメラ・マイクは自分だけ、位置・支払いは無し)、本番だけ HSTS(1年・サブドメイン)。
  `/api/*` は `Cache-Control: no-store`(領収書の画像は `private, no-store`)。
- **領収書の画像の配信**(`GET /api/receipts/:id/image`): 署名付きURLへ転送せず、API がセッションの Cookie で閲覧できる人
  (本人・管理者・コーディネーター)を確かめてから中身を返す。署名付きURLは期限内なら URL だけで誰でも読め(履歴・共有・
  Referer から漏れうる)、CSP の `img-src` に GCS を足す必要もあるため使わない。`Content-Type` は保存時と同じく中身の先頭バイトで
  判定し直した JPEG / PNG / WebP だけ(それ以外は 404)、`nosniff` と `private, no-store` を付ける。閲覧の記録は一覧の単位
  (他のスタッフ・全スタッフ分の一覧は「もっと見る」の続きのページも含めて1ページごとに INFO `receipt.list.viewed`、CSV は INFO
  `receipt.list.exported`)で残し、1枚ごとには残さない(サムネイルの表示のたびに記録が増えるため)。続きのページも残すのは、続きの位置
  (`cursor`)は利用者が書き換えられ、最初のページの記録だけでは読んだ範囲を追えないため。続きの位置は DB に渡す前に形(UUID・
  0001〜9999年の実在する日時)を確かめ、誤りは 400(`invalid_cursor`)。断った閲覧は WARN(`receipt.image.view_denied` 等)。
- **画面**: JSX で描く(GAS版の innerHTML の組み立てはしない)。localStorage には個人情報を含む値をその人のキーだけに置き、
  ログアウトで消す(`packages/web/README.md`)。

## 6. 入力の上限と資源の保護

| 対象 | 上限 |
| --- | --- |
| 要求の本体 | 既定 256KB、領収書の登録 14MB、OCR 3MB、外部システムからの顧客 2MB(413) |
| 領収書の画像 | 1回6枚、1枚1.5MB(Base64 を戻した後)、JPEG / PNG / WebP を中身の先頭バイトで判定。1枚でも不正なら何も保存しない |
| テキスト | AI に渡すメモ 20,000字、APIキー 500字、Webhook URL 2,000字、モデル名 200字 等(契約の `max`) |
| パスワード | 128文字 |
| DB | ロールごとの `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout`(アプリ 15s / 5s / 30s、ワーカー 60s / 10s / 60s) |
| 従量課金 | AI 生成 1日200回、OCR 1日300回、ルートの再計算 1時間30回(スタッフごと) |
| 外部システム連携 | 顧客の受け取り 1時間120回(API キーごと)、1回500件 |
| ジョブ | `JOB_TIMEOUT_MS`(既定30分) |

大量の要求そのものは Cloud Run に届く(Cloud Armor は未導入。11章)。

## 7. 外部への送信(SSRF など)

- Google Chat の Webhook: 保存時と送信時に `https://chat.googleapis.com/v1/spaces/<space>/messages?…` の形だけを許す
  (`domain/notifications/googleChatWebhook.ts`)。リダイレクトは追わず、10秒で打ち切り、失敗の記録に応答本文を残さない。
- Gemini のキーはヘッダー(`x-goog-api-key`)で送る。GAS Bridge のシークレットはクエリにも載る(受け入れているリスク。11章)。
- 送信元IP(ログ・回数制限)は `X-Forwarded-For` の右から `TRUSTED_PROXY_HOPS` 番目(Cloud Run 直は1、外部ロードバランサを前に
  置くなら2、0 なら接続元)。利用者が偽装した値は左側に並ぶため使わない。

### 7.1 Web Push(翌日の予定のお知らせ)

- **送り先**: ワーカーは登録された購読の `endpoint` へ POST するため、API は既知のプッシュサービス(FCM・Mozilla・Apple・Windows)の
  `https` の URL だけを受け付ける(`@katahimo/shared` の `isAllowedPushEndpoint`。認証情報・ポートつきの URL も拒否)。DB も `https://`
  以外を CHECK で拒否する。
- **中身を小さくする**: 通知はロック画面に出て、プッシュサービス(Google・Apple 等)を通る。中身は端末の鍵で暗号化(RFC 8291、
  `aes128gcm`)されプッシュサービスには読めないが、入れるのは予定の時刻とお客様のお名前だけにする(住所・電話番号・予約詳細や
  ルートの URL は入れない。見るには通知を押してログインしたアプリの予定タブを開く)。outbox の `push.*` のペイロードも同じ文面だけで、
  送り終えた(`done`)ものは完了から7日、送れなかった(`failed` / `dead`)ものは90日で保守のジョブが消す(`RETENTION_DAYS.outboxDone` /
  `outboxFailed`、03 9章)。
- **購読は本人の端末だけ**: 登録・削除はセッションのスタッフのものだけ(要求にスタッフの指定は無い)。同じ端末で別の人が通知を
  オンにしたら、その人の購読に付け替わる(前の人には届かなくなる)。積んだ後に付け替わった端末には前の人の通知を送らない。
  ログアウトは(どの画面からでも)ログアウトの前に本人がオンにしていた端末の購読をサーバーと端末でやめ、ログインしたときは、本人が
  オンにしたのではない端末の購読(前にその端末を使った人のもの)を端末でやめる。セッションの期限切れでは止めない(本人の端末を
  しばらく開かなかっただけで通知が止まらないように)。退職日を今日以前にすると(セッションの失効と同時に)購読を全て消し、お知らせの日に在籍していない人には送らない。
  `endpoint` と鍵は操作ログ・例外の文に残さない。
- **古いお知らせを出さない**: お知らせには期限があり(「明日の予定」はその日の0時まで)、過ぎたら送らない(05 10.1)。
- **VAPID の秘密鍵**: 送信の署名に使う `VAPID_PRIVATE_KEY` はワーカーだけが Secret Manager から読む(API は公開鍵だけを持つ)。
  漏れると第三者が購読へ通知を送れる(中身の暗号化には端末の鍵が要るが、送り先の endpoint を知っていれば送れる)ため、疑わしければ
  鍵を作り直し(07 8.3)、スタッフが通知をオンにし直す。
- 回数と数の上限: テスト通知は1時間10回、購読の登録は1時間30回、購読は1人10件まで(古いものから消す)。プッシュサービスが
  「もう無い」(404 / 410)と答えた購読はすぐ、それ以外の 4xx で3回続けて断られた購読も消す。

## 8. 保存データの保護

### 8.1 方針

保存データは **CMEK(Google Cloud の利用者=運用側が管理する暗号鍵)によるディスク・バックアップ単位の暗号化**で守り、データを読める人と経路を
**RLS・最小権限・監査ログ・回数制限**で絞る。列は型つきで持つ(03 8章)。

参考: 医療情報を扱うシステムの国の指針(厚生労働省「医療情報システムの安全管理に関するガイドライン 第6.0版」、経済産業省・総務省「医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン」。合わせて「3省2ガイドライン」)は保存データの暗号化を対策の一つに挙げており、項目(列)ごとの暗号化は必須としていない。米国 HIPAA の Security Rule でも保存時の暗号化は addressable(状況に応じて実施)。本アプリは医療機関ではなく、これらへの準拠・認証を主張するものではない(水準の目安として参照。版・条項は要確認)。

| 保管場所 | 鍵(Cloud KMS、asia-northeast1) | 暗号化する範囲 |
| --- | --- | --- |
| Cloud SQL | `katahimo/cloudsql-cmek` | データのディスク・自動バックアップ・ポイントインタイムリカバリのログ・リードレプリカ |
| 領収書画像(GCS) | `katahimo/storage-cmek` | バケットの全てのオブジェクト(古い版を含む) |
| テナントの秘密値 | `katahimo/tenant-secrets` | `tenant_secrets` の値そのもの(SecretBox。8.3) |

鍵の中身は Cloud KMS の外に出ない。暗号化・復号は Cloud SQL・GCS のサービスエージェント(と秘密値は API の実行SA)だけが
鍵の権限 `roles/cloudkms.cryptoKeyEncrypterDecrypter` で行う(`infra/gcp/kms.tf`)。鍵は90日ごとに自動でローテーションする
(新しい鍵バージョンを GCS は以後に書くオブジェクトに使う。Cloud SQL は既存のインスタンスを新しい主バージョンで自動では
暗号化し直さない。揃えるなら `gcloud sql instances reencrypt`。要確認)。
鍵の運用と、鍵を失ったときの扱い(データも失う)は [07](07_インフラ・運用.md) 3.8。

### 8.2 CMEK が守るもの・残るリスク

| 脅威 | CMEK で | 残るリスクと補う対策 |
| --- | --- | --- |
| ディスク・バックアップ・バケットの中身の持ち出し(媒体・スナップショット・誤って共有したバックアップ) | 守れる。鍵の権限の無い者には読めない | — |
| バックアップを別のインスタンス・プロジェクトに戻す | 守れる(戻す側に鍵の権限が要る) | — |
| エクスポート(`gcloud sql export`)の書き出し | 守れない(書き出したファイルは出力先バケットの鍵で暗号化される) | export の権限を運用の責任者だけにする。出力先バケットも CMEK にする(07 3.8)。Cloud Audit Logs に残る |
| 緊急時の封じ込め(鍵のバージョンを無効にすると全テナントのデータが読めなくなる。解約には使わない) | 鍵のバージョンを無効にすると、そのインスタンス・バケットのデータを読めなくなる | 止めるとアプリも止まる。テナントの消去は `platform.purge_tenant()`(テナント単位) |
| アプリ・DB ユーザーの権限を使った読み出し(アカウントの乗っ取り、コードの不具合、SQL インジェクション) | 守れない(正規の経路では平文で読める) | テナントの分離は FORCE RLS と複合外部キー(3章)、ロールごとの最小権限、SQL はパラメータ化(Drizzle)、閲覧・書き込みの監査ログ(10章)、ログインの回数制限・ロック(2章) |
| 権限を持つ運用者・プロジェクトの管理者 | 守れない | IAM を最小にし、Cloud KMS・Cloud SQL の管理操作は Cloud Audit Logs に残る(07 3.8) |
| 利用者の端末・画面からの漏えい | 対象外 | Cookie のセッション・ログアウトで端末の保存値を消す(5章) |

CMEK の鍵で暗号化されない場所にも個人情報がある。それぞれのサービスの既定の暗号化(Google 管理の鍵等)と、送る・残す量を
絞ることで守る。

| 場所 | 載る個人情報 | 暗号化 | 絞り方 |
| --- | --- | --- | --- |
| Google Workspace の Google Calendar | 予定の件名(お客様の名前)・場所(住所) | Google Workspace の既定 | 予定は会社の Workspace のまま(アプリは読むだけ)。カレンダーの共有を会社の中に限る |
| Google Workspace の Google Drive(顧客CSV) | RESERVA の顧客CSV(お客様・お子様・緊急連絡先) | 同上 | 取込用のフォルダの共有を運用の責任者とジョブの SA だけにする。どのフォルダを読むかは運用担当者がテナントごとに決める(05 5章) |
| Google Workspace の Sheets・Drive(GAS Bridge のミラー) | 出勤簿・日報・事故報告・領収書の画像の写し | 同上 | ミラーは任意(`MIRROR_TO_GOOGLE_SHEETS=false` で送らない)。送るのは GAS版を並行して使う間だけ、Bridge の持ち主のテナント(`GAS_BRIDGE_TENANT`)の記録だけ(05 2.1・9章) |
| Gemini API | 日報・事故報告のメモ・領収書の画像 | Google の既定 | 送るのは利用者が AI の下書き・読み取りを押したときだけ。キーを設定しなければ呼ばない。データを学習に使わない条件の有料の API キーを使う(要確認) |
| Google Chat(Webhook) | 日報・事故報告・領収書のお知らせ(スタッフ・お客様の名前、本文) | Google Workspace の既定 | 送り先は会社の Google Chat のスペースだけ(7章)。Webhook URL を設定しなければ送らない |
| メール(SMTP) | 再設定コード・宛先のメールアドレス | 送信経路の TLS(送信先による) | 本文はコードだけ。お客様の情報は送らない |
| Cloud Logging | 要求の記録(パス・状態・所要時間・IP) | Google 管理の鍵 | 個人情報の値をログに出さない(`app_logs.details` も ID・件数・理由コードだけ。10章) |
| Secret Manager | 実行時の秘密値(DB のパスワード・`SESSION_SECRET` 等) | Google 管理の鍵 | アクセスを実行SAだけにする(9章) |
| Terraform の state のバケット・エクスポートの出力先 | 構成情報(state)・DB の書き出し(エクスポート) | バケットの鍵(既定は Google 管理) | state に秘密の値を入れない。エクスポートの出力先は CMEK にし、権限を運用の責任者だけにする(07 3.8) |
| 利用者のブラウザの localStorage | 最近開いたお客様・書きかけの日報(その人のキーだけ) | 端末による | ログアウトで消す(5章。キーは `packages/web/README.md`) |

### 8.3 テナントの秘密値(SecretBox)

Gemini の API キー・Google Chat の Webhook URL は、盗まれるとそのまま外部サービスを使われるため、保管場所の暗号化に加えて
値そのものを Cloud KMS の `tenant-secrets` で暗号化して `tenant_secrets.sealed_value` に置く(`packages/integrations/src/secret-box`)。
暗号文はテナントIDと秘密値の名前に結び付き、別の行に写しても開けない。開けるのは API の実行SAだけ(ワーカーは表も読めない)。
開発は `SECRET_BOX_LOCAL_KEY`(`.env`)。鍵や実装を変えると保存済みの値は開けないため、管理者設定で保存し直す。
開けない値は例外にせず「設定済み・読めない」として扱う(ERROR `settings.secret.unreadable`、値は記録しない)。管理者設定の画面は開け、
その項目は設定済み・伏せ字なしで出る。入力し直して保存すると比べずに上書きする。AI の下書き・読み取りと Google Chat の通知は、
開けないときは `.env` の既定(`GEMINI_API_KEY`・`GCHAT_*_WEBHOOK_URL`、無ければ使わない)に戻し、日報・領収書の保存は失敗させない。

| 鍵・秘密 | 置き場所 | 用途 | 変えると |
| --- | --- | --- | --- |
| `tenant-secrets`(Cloud KMS) | Cloud KMS(90日ごとに自動ローテーション) | テナントの秘密値の封 | ローテーションは古い版が残るので読める。鍵を別の鍵に替えたら秘密値を保存し直す |
| `SECRET_BOX_LOCAL_KEY` | `.env`(開発だけ) | 同上 | 保存済みの秘密値が開けなくなる(保存し直す) |
| `SESSION_SECRET` | Secret Manager `katahimo-session-secret` | 再設定コードの HMAC・回数制限のキーの導出(HKDF で用途ごと) | 送信待ちの再設定コードが使えなくなり、回数制限の数え直しになる(セッションは DB の行なので切れない) |

本番は `SECRET_BOX_PROVIDER=gcp` でなければ API が起動しない。

### 8.4 次に強めるところ

- **管理者の多要素認証**: 管理者は全スタッフ・全顧客のデータと秘密値の設定を扱えるため、乗っ取られたときの影響が最も大きい。
  管理者(`admin` / `coordinator`)のログインに TOTP 等の2要素目を足す(未実装)。
- **担当のお客様だけを閲覧できるようにする**: 今は GAS版と同じく全スタッフが全顧客の詳細を開ける。担当(予定・予約の割り当て)の
  あるお客様だけに絞れば、1人のアカウントが乗っ取られたときに読まれる範囲が小さくなる(未実装。11章)。

## 9. 秘密値の管理

- ソースに書かない。ローカルは `.env`(`.gitignore` 済み。`.env.example` に項目と説明)、本番は Secret Manager から Cloud Run の
  環境変数に入れる。サービスアカウントは自分の使う secret だけを読める(`infra/gcp/secrets.tf`)。
- テナントごとの秘密値(Gemini のキー・Chat の Webhook URL)は `tenant_secrets` に SecretBox で封をして置き(本番は Cloud KMS の
  `tenant-secrets` で暗号化。8.3)、画面には伏せ字と設定済みの印だけを返す
  (`SECRET_MASK_CHAR`)。伏せ字のまま保存しても値は変わらず、伏せ字の一部だけ書き換えた値は拒否する。
- 本番の起動時の検証(`NODE_ENV=production`): (API)`SECRET_BOX_PROVIDER=gcp` + `SECRET_BOX_KMS_KEY`、`STORAGE_PROVIDER=gcs` + `GCS_BUCKET`、
  `SCHEDULE_PROVIDER` の明示、(API)32文字以上の `SESSION_SECRET`、(ワーカー)`SMTP_HOST`。足りなければ起動前に落ちる。
  ワーカーは VAPID の3つ(`VAPID_PUBLIC_KEY`・`VAPID_PRIVATE_KEY`・`VAPID_SUBJECT`)が揃っていない(一部だけ)と起動しない。

## 10. 監査ログ・記録の保全

- 操作ログは `AppLogPort.write`(`app_logs`、月のパーティション、アプリ・ワーカーは追記だけ)。規則は GAS版 `logToBuffer` と同じ:
  WARN / ERROR / SECURITY と全ての書き込みは必ず残し、読み取りの成功はお金のかかるもの(地図)と、他のスタッフのデータを扱ったとき
  (`targetStaffId`)、要配慮情報の閲覧(`customer.detail.viewed`)だけ残す。ポートは例外を投げない。
- `details` には ID・件数・理由コードだけを入れる(個人情報・本文・秘密値は入れない)。ログインIDはマスクして残す。
- 1要求1行のプロセスログ(`http/requestLog.ts`)はパスとステータスだけ(クエリ・本文は残さない)。リクエストIDで app_logs と結び付く。
- 閲覧: 管理者は「🛠 管理」→「操作ログ」(`GET /api/admin/audit-logs`・`.csv`)で自分のテナントの記録だけを読める。読み出しは UoW の
  トランザクションで RLS(`app_logs_select`: `tenant_id = app_current_tenant()`)を通し、リポジトリも `tenant_id` で絞る。
  tenant_id が null の記録(法人が決まる前のログイン失敗・再設定の要求等)はどのテナントの管理者にも見せない(誰のものか確かめられない
  ため。運用者が DB / Cloud Logging で見る)。閲覧(INFO `audit_log.viewed`)とダウンロード(SECURITY `audit_log.exported`)も記録し、
  期間は93日まで。CSV は表計算ソフトの式として実行されないよう `=`・`+`・`-`・`@` で始まる値に `'` を付ける。
- 全員分の日報・事故報告(「🛠 管理」→「報告一覧」)は、他のスタッフの記録を含む一覧(続きのページも1ページごとに INFO `report.list.viewed`、`details.continued`)・他のスタッフの記録の
  中身(INFO `report.detail.viewed`)・CSV の書き出し(SECURITY `report.list.exported`、期間は366日まで)を記録する。本文は `details` に
  入れない(条件・件数・記録のIDだけ)。CSV の式の扱いは操作ログと同じ(`http/csv.ts`)。
- 出勤簿の Excel の書き出し(02 8.6)は、本人の分も含め毎回 INFO `attendance.export.downloaded`、管理者の全員分は
  SECURITY `attendance.export_all.downloaded`(人数)で残す。回数の上限(`attendance_export_staff`)があり、全員分は管理者だけ(`requireAdmin`)。
  セルの文字は文字列として書くため、`=` で始まる店名・備考などが式として実行されることはない(式は計算の列だけにアプリが書く)。
- 管理者の書き込み(スタッフの登録・変更・削除・案内メール、AIプロンプト、設定)は SECURITY / INFO で残し、断った操作は WARN
  (`…_rejected`、`details.reason`)。スタッフの変更は変えた項目名だけを残す(住所・電話等の値は残さない)。
- 記録の保全: 確定済みの記録(`KH002`)・締めた月(`KH001`)はトリガーが拒否し、解除は運用者だけ。記録の本文の変更前は
  `care_record_revisions`、出勤簿の変更前は `entity_changes.before` に残る(どちらも追記だけ)。
