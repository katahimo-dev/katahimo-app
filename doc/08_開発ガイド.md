# 08. 開発ガイド

- 目的: ローカルで動かす準備、コマンド、コードの書き方の決まり、テストの考え方、機能を1つ足すときの手順をまとめる。
- 対象読者: このリポジトリで開発する人(人・コーディングエージェントとも)。

画面の書き方の決まりは [`packages/web/README.md`](../packages/web/README.md)、エージェント向けの要約は [`CLAUDE.md`](../CLAUDE.md)。

## 1. ローカルの準備

必要なもの: Node.js 22 以上、pnpm 11(`package.json` の `packageManager`。`corepack enable`)、PostgreSQL 16 以上(直接か Docker)。

```bash
git clone --recurse-submodules https://github.com/katahimo-dev/katahimo-app.git
cd katahimo-app
git submodule update --init     # 既に clone 済みで legacy/ が空のとき(GAS版を読めるトークンが要る)
pnpm install
```

`legacy/gas-childcare-visit-app` は GAS版との一致テスト(gasParity)が使う(無ければスキップされる)。GAS版の最新に
追従するときは `git submodule update --remote legacy/gas-childcare-visit-app` のあと参照コミットをコミットする。

### 1.1 データベース

```bash
# PostgreSQL を直接入れている場合(:5432)。ロール(03 5章)と DB katahimo_dev を作る(何度流してもよい)
psql -U postgres -h localhost -f infra/initdb/00_create_database.sql            # -v dbname=<名前> で別の DB
psql -U postgres -h localhost -d katahimo_dev -f infra/initdb/01_bootstrap.sql
# Docker の場合(:5433。初回の起動で上の2本が流れる)
docker compose -f infra/docker-compose.yml up -d
```

### 1.2 `.env`

```bash
cp .env.example .env
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # SECRET_BOX_LOCAL_KEY に入れる
```

| キー | 値(Docker なら :5433) |
| --- | --- |
| `DATABASE_URL` | `postgres://katahimo_app:katahimo_app@localhost:5432/katahimo_dev` |
| `WORKER_DATABASE_URL` | `postgres://katahimo_worker:katahimo_worker@localhost:5432/katahimo_dev` |
| `MIGRATION_DATABASE_URL` | `postgres://katahimo_migrator:katahimo_migrator@localhost:5432/katahimo_dev` |
| `SESSION_SECRET` | 任意(16文字以上。本番は32文字以上) |
| `SECRET_BOX_LOCAL_KEY` | 64桁 hex(テナントの秘密値の封に使う開発用の鍵) |

ほかは空でも動く: 予定は `noop`(常に0件)、AI・OCR は「API Key Missing」、再設定メールは `pnpm worker` の標準出力、通知は送らない、
領収書の画像は `./data/receipts`(API の作業フォルダから)。`SECRET_BOX_LOCAL_KEY` を変えると、
管理者設定で保存した秘密値(Gemini のキー・Webhook URL)が開けなくなる(保存し直す)。各項目の説明は `.env.example`。

### 1.3 マイグレーション・開発用データ・起動

```bash
pnpm db:migrate   # MIGRATION_DATABASE_URL(katahimo_migrator → 所有者)で packages/db/drizzle を適用
pnpm db:seed      # テナント demo、admin@ / coordinator@ / staff@example.com(パスワードは全員 admin1234)、お客様3件(何度流してもよい)

pnpm --filter @katahimo/api dev      # API  http://localhost:8080(/api/health・/api/health/db)
pnpm --filter @katahimo/web dev      # 画面 http://localhost:5173(/api は :8080 へ中継。WEB_DEV_PORT / WEB_API_PROXY_TARGET)
pnpm worker                          # outbox(再設定メール・ミラー・Web Push)を試すときだけ
```

ローカルの API は `OUTBOX_DRAIN_JOB` が無いため、outbox に積んでも outbox-drain(本番の Cloud Run Jobs)の起動を頼まない。
積んだものは `pnpm worker`(ローカル開発専用の見回り。`OUTBOX_POLL_INTERVAL_MS` ごとに空になるまで処理する。`NODE_ENV=production`
では起動しない)か、必要なときに `pnpm outbox:once`(本番の outbox-drain と同じ処理を1回)で送る。夜間ジョブは `pnpm job:*` で
1回ずつ流す(`job:route-notice`・`job:nightly-calendar-sync` は本番と同じく、積んだ outbox を最後にそのジョブの中で送る)。

`http://localhost:5173/?t=demo` を開き `admin@example.com` / `admin1234` でログインする。

本番と同じ形(API がビルド済みの画面を同じオリジンで配信)で動かすには `pnpm build` のあと `WEB_DIST_DIR=<packages/web/dist の絶対パス>`
を付けて API を起動する。ただし `packages/*/dist` は外部依存をバンドルしないため、ワークスペースの `node_modules` からは動かない。
`Dockerfile` と同じく本番依存を平坦に入れたフォルダ(`pnpm install --prod --frozen-lockfile --config.node-linker=hoisted --filter '@katahimo/api...'`)
に置いて動かす。

| `pnpm import:legacy-reports -- <slug> --spreadsheet <ID> [--dry-run]` / `pnpm import:legacy-receipts -- <slug> --spreadsheet <ID> --month YYYY-MM [--dry-run]` | GAS版の日報・事故報告シート / 領収書一覧からの移行の取込(Google の ADC が要る。05 12章・09 2.4) |
| `pnpm worker` | ローカル開発専用の outbox の見回り(本番のイメージには入らない。1.3) |

| `pnpm push:vapid-keys` | Web Push の VAPID の鍵(公開鍵・秘密鍵)を作る。ローカルで通知を試すなら `.env` の `VAPID_*` に入れる(05 10章) |
| `pnpm e2e [-- --only <正規表現>]` | 実際の API・DB での通し確認(API・Vite が動いていなければ起動する。DB に書く。開発だけ) |

一部だけのテスト: `pnpm vitest run packages/core/src/domain/attendance`、`pnpm vitest run --project integration`、`pnpm vitest run --project web`。

読む(`packages/api/src/scripts/cliArgs.ts` の `cliArgs()`、`tools/e2e/src/e2e.ts`)。`pnpm --filter …` のスクリプトは
パッケージのフォルダで動くため、入力ファイルの相対パスは `INIT_CWD`(コマンドを打ったフォルダ)から解決する(`resolveInputPath()`)。

## 3. 書き方の決まり

### 3.1 GAS版からの移し方

- **振る舞いを写し、書き方は写さない**: 画面のクラス名・日本語の文言・出力・検証の文言・端の場合は GAS版と同じにする。
  innerHTML の組み立て(→ JSX)、名前・行番号での特定(→ ID)、列記号のばらまき(→ レイアウトの層だけ)、クライアントの言うスタッフを
  信じる、シートの丸ごとの書き換え(→ 差分)、隠れたグローバルな状態は写さない。
- ロジックは `core/domain` の純粋関数にしてテストを書き、I/O はポートの向こうに置く。
- GAS版の不具合は直して、違いを記録する([02 11章](02_機能仕様.md)・`packages/web/README.md`)。
- サブモジュール `legacy/` は読み取り専用。GAS版を直すときは GAS版のリポジトリで直して参照コミットを上げる。

### 3.2 層と依存

- usecase は Drizzle に触らない。`deps.uow.run(tenantId, async (r) => …, { actorId })` の中でリポジトリだけを使う(03 4.3)。
  外部 API はトランザクションの外。`run` の中で2本目の接続・ネットワークの呼び出しが要る処理を書かない。
- ドメインの書き込みと outbox は同じ `run` の中。
- 新しい外部依存はポート(`core/ports`)を切り、実装を `integrations`(DB なら `db`)に置き、`api/src/container.ts`・
  `worker/src/container.ts` で組み立てる。テスト用のインメモリ実装を `core/src/usecases/testDoubles.ts` に足す。
- 外部のサービスを呼ばない、ファイルの形を作るだけのライブラリ(出勤簿の .xlsx の `exceljs`)はポートにせず、使う層に置く
  (`api/src/export/`)。何を書くか(列・計算式・値の形)は `core/domain` の純粋な定義にし、ライブラリの側は並べて見た目を付けるだけにする。
- API とワーカーで同じでなければならない環境変数は `integrations/src/runtime-env/sharedEnv.ts` の `sharedEnvShape`。
  環境変数を足したら `.env.example`・`infra/gcp/run.tf`(本番)・資料も直す。

### 3.3 契約とエラー

- 要求・応答の形は `packages/shared/src/contracts/` の zod スキーマだけで決める(04 4章)。
- 失敗は `DomainError(code, message, fields?, reason?)`。`message` は利用者に出す日本語。外部サービスの失敗は一般的な文言の 502 にし、
  詳細はログだけに。
- ファイルを返す API(操作ログの CSV・出勤簿の .xlsx)は、要求だけを契約のスキーマで確かめ、応答は `Content-Disposition`
  (`api/src/http/download.ts` の `attachmentDisposition`: ASCII の `filename` と RFC 5987 の UTF-8 の `filename*`)・`Cache-Control: no-store`。
  画面は `<a download>` ではなく `api.download()`(`web/src/api/client.ts`)で受け、断られたときはふつうの API と同じエラーにして
  お知らせを出す(理由の JSON をファイルとして保存させない)。
- 同時に編集されうる行は `rowVersion` を契約に出し、更新に省略可能な `rowVersion` を受ける(03 7章)。

### 3.4 ログ

`AppLogPort.write({ tenantId, level, action, actorStaffId, targetStaffId, details, ...actor.meta })`。レベルは
`INFO` / `WARN` / `ERROR` / `SECURITY`、action は点区切り(`report.daily.saved`・`schedule.route.failed`)。WARN / ERROR / 拒否と全ての
書き込みは必ず残し、読み取りの成功はお金のかかるものと他人のデータを扱ったときだけ残す。`details` に個人情報・本文・秘密値を入れない。

### 3.5 出勤簿の列記号

DB は実体(`attendance_days` + `visits` / `work_segments` / `travel_legs`)。列記号(`C` … `AO`)の `rowData` は投影で、
`packages/core/src/domain/attendance/sheetLayout.ts`(`projectDay` / `applyRowEdit`)だけが知っている。画面側の対応は
`packages/web/src/features/attendance/model/dayRecord.ts`。ほかの場所では名前つきの定義(`VISIT_SLOTS`・`MOVE_LEGS`・`SLOT_DEFS`…)を
使い、列記号を書かない。`gasParity.test.ts` を常に通す。例外は出勤簿の Excel の書き出しの列の定義
`packages/core/src/domain/attendance/sheetTemplate.ts`(テンプレートと同じ列の並び・計算式を Excel の列記号で持つ。入力の列は
`rowData` のキーと同じ列記号)。

### 3.6 その他

- コメント・資料・README・CHANGELOG・コミットメッセージは日本語(`CLAUDE.md` だけ英語)。
- 秘密値はソースに書かない。
- ID はアプリが UUIDv7 で採番する(`core/domain/ids` の `newId()`)。
- 業務日・時刻は端末の時刻帯に関係なくテナントの時刻帯(既定 JST)で数える。
- 利用者・運用に見える変更は `CHANGELOG.md` に書く(`## [Ver. x.y.z] - 日付`)。

- 結合テストのテナントは毎回乱数の slug で作る(`db/src/integration/testDb.ts`)ので、同じ DB で何度流してもよい。

## 5. 機能を1つ足す手順

例: 「お客様にメモを足す API と画面」。

1. **仕様**: GAS版に同じ機能があればその振る舞い・文言を確かめる。[02_機能仕様.md](02_機能仕様.md) に画面・ルール・権限を書く。
2. **DB**(要るなら): スキーマを変え → `pnpm db:generate` → 手書きが要るもの(GRANT・FORCE RLS・トリガー)を `--custom` のマイグレーションに
   → `pnpm db:migrate` → `pnpm db:doc`([03 11.2](03_データベース設計.md))。自由記述は `text`、構造のある値は `jsonb` の型つきの列にする。
3. **契約**: `packages/shared/src/contracts/` に要求・応答のスキーマ。
4. **ドメインと usecase**: 純粋なルールは `core/domain`、流れは `core/usecases`(UoW・権限・ログ)。単体テスト。
5. **リポジトリ・アダプター**: `db/src/repositories/tenant/*`(と `core/ports` のインターフェース)、外部なら `integrations`。結合テスト。
6. **ルート**: `api/src/routes/*` で `requireSession` / `requireAdmin`・`parseJsonBody`・`jsonOk`。`routes.integration.test.ts` に権限とエラー。
   [04_API仕様.md](04_API仕様.md) に行を足す。
7. **画面**: `packages/web/src/api/<機能>.ts` → `features/<機能>/`(GAS版のクラス名・文言、`packages/web/README.md` の決まり)。画面のテスト。
8. **確認**: `pnpm lint && pnpm typecheck && pnpm test && pnpm build`、`pnpm docs:check`。`CHANGELOG.md` に書く。

## 6. 資料のリンクの確認

`pnpm docs:check` が git 管理(と未追跡)の `*.md` の相対リンクのリンク切れ、閉じていないコードブロック、種類の分からない mermaid を
見つける(見出しへのリンク `#…` の先までは確かめない)。資料を直したら流す。
