# 目的

ベビーシッター法人向けマルチテナントSaaS(将来は訪問看護にも展開)の技術構成について、外部アドバイザーの意見を求めるための簡潔な要約。詳細は `docs/07_技術構成提案書.md` を参照。

---

# 1. 全体構成

| レイヤー | 選定 | 根拠(一言) |
|---|---|---|
| データベース | **PostgreSQL** | 予約重複防止・請求整合性・カルテ改訂管理をDB制約(RLS/EXCLUDE制約/生成列)で強制できる。MySQL等は同等の制約を自作する必要があり実装コストが高い |
| マルチテナント方式 | shared schema + `tenant_id` + Row Level Security | スキーマ分岐(テナント別スキーマ/DB)は将来の業種拡張(訪問看護)で保守が破綻しやすいため回避 |
| 実行基盤 | **Google Cloud Run** | Calendar/Maps/Gemini等の既存連携がすべてGoogle系。単一クラウドに統合し運用の複雑さと費用を抑える |
| 認証 | Firebase Auth / Identity Platform | メール+パスワードで5万MAUまで無料。自前実装よりセキュリティ・運用コストで有利 |
| バックエンドAPI | **Hono** | Cloud Run公式デプロイガイドが存在し移植リスクが低い。軽量でテナント切替ミドルウェアが書きやすい |
| フロントエンド(現場スタッフ用PWA) | **Vite + React SPA + `vite-plugin-pwa`** | スマホでのオフライン耐性・インストール性が最重要。枯れたPWA専用プラグインがある |
| フロントエンド(管理画面) | Next.js または 同上のVite SPA(要決定、後述) | CRUD/フォーム中心の管理画面としてはどちらも妥当 |

---

# 2. データベース比較(要点)

| 候補 | 一言評価 |
|---|---|
| **PostgreSQL(推奨)** | RLS・排他制約・生成列で、本システムが必要とする整合性をDB機能だけでほぼ満たせる |
| MySQL/MariaDB | 実績はあるが上記の制約に相当する機能がなく自作コストが高い |
| Cloud Spanner / CockroachDB | この規模には過剰性能・過剰投資 |
| SQL Server | GCP中心の構成と相性が薄く採用理由が乏しい |

# 3. 開発フレームワークのおすすめ

## バックエンド: Hono を推奨
NestJS・Fastify・Expressと比較検討。Google公式のCloud Runデプロイガイドがあり、既存検討(Cloudflare Workers前提)からの移植リスクが低いこと、軽量でマルチテナント用ミドルウェア(テナントごとのDB接続コンテキスト切替)を書きやすいことが決め手。

## フロントエンド: 用途によって使い分けを推奨
本システムは「現場スタッフ用スマホPWA」と「管理者用の管理画面」という性質の異なる2つの画面群を持つため、フレームワークも分けるのが合理的。

- **現場スタッフ用PWA → Vite + React SPA + `vite-plugin-pwa`**。オフライン対応・ホーム画面インストールに強く、最も枯れた選択。
- **管理画面 → Next.js(App Router) と Vite SPA のどちらも妥当、決め手次第**。

  | 観点 | Next.js | Vite SPA |
  |---|---|---|
  | 管理画面向けライブラリの豊富さ・採用人材の見つけやすさ | ◎ | ○ |
  | Cloud Runへのデプロイの単純さ | ○(standalone出力) | ◎(静的配信のみ) |
  | ビルド系統の一本化(PWA側と揃える) | △ | ◎ |

  将来、管理画面に検索エンジン最適化(SEO)や公開ページが必要になる可能性があればNext.js、開発体制を1つのビルド系統(Vite)に揃えたいならVite SPAが決め手になる。**現時点でどちらも技術的に妥当なため、この点は要検討事項の一つとしたい。**

参考: iOS Safariのプッシュ通知はホーム画面への追加(PWAインストール)が前提となる制約があるが、これはフレームワークに依存しないプラットフォーム側の制約。

## 将来のネイティブアプリ化(React Native)
ジオフェンス(訪問先の到着/退出検知)機能のため将来React Native化を検討中。認証(`@react-native-firebase/auth`)・DB(変更不要、Hono API経由)のアーキテクチャは維持できるが、オフライン同期(`expo-sqlite`のoutboxパターン)が新たに必要。詳細は `docs/07_技術構成提案書.md` 第12章を参照。

# 4. コスト方針(概要)

| フェーズ | DB | 月額目安 |
|---|---|---|
| Phase -1: クリック試作品 | ブラウザ内DB(PGlite)、サーバー無し | ¥0 |
| PoC | Neon または Supabase の無料枠(2択。判断基準は`docs/07_技術構成提案書.md` 11.2節) | ほぼ¥0 |
| 本番(実顧客データ投入後) | Cloud SQL for PostgreSQL(東京リージョン) | 概算¥5,000〜14,000/月(HA構成の有無による) |

Cloud Run/Secret Manager/Firebase Auth等は本規模ではほぼ無料枠内。**コストの固定費要因は実質Cloud SQLのみ**。金額は2026年8月時点の概算であり、発注前に公式料金ページで再確認する前提。
