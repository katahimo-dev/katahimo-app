# 1. エグゼクティブサマリー

現行の `gas-childcare-visit-app`(Google Apps Script)は単一法人向けの業務ツールとして機能しているが、以下を実現するには技術基盤の刷新が必要である。

- 複数の法人(テナント)を安全に収容するマルチテナントSaaS化
- 予約管理・請求/決済(settlement)・カルテ的な記録機能の追加
- 法人ごとに異なる既存データ形式を取り込める、プラガブルなデータ取込層
- 将来的な訪問看護事業者への展開(カルテ・記録の厳格な改訂管理・保存年限が必要になる)

本書の結論は以下の3点。

1. **データベースはリレーショナルDB、具体的にはPostgreSQLを推奨**する(比較検討は第3章)。予約の二重登録防止・請求明細の整合性・カルテの改訂履行など、本システムが要求する制約の大半をDBの機能そのもので強制できるためである。
2. **実行基盤はGoogle Cloud Platform(GCP)、Cloud Runを中核**に据える。既存の連携先(Google Calendar、Google Maps、Gemini API)がすべてGoogle系であるため、単一クラウドに統合することで運用の複雑さと費用を抑えられる。
3. **PoC(概念実証)段階のコストを抑えるため、DBのホスト先をフェーズごとに変える**。開発はローカルSQLite、PoCはNeonまたはSupabase(いずれもサーバーレスPostgres、無料枠で運用可能。判断基準は第11.2章)、本番は東京リージョンのCloud SQL for PostgreSQLへ、という段階移行を採る(第11章)。

想定スケールは初期数社・各社スタッフ10名程度・顧客100名以上。将来的に年数社ペースでテナントが増える前提で設計するが、今回の技術選定は「今の規模でも無駄なく動き、後で詰まらない」ことを優先している。

# 2. 現状システムの棚卸し

技術選定の前提として、現行 `01_GAS/gas-childcare-visit-app` の実態を整理する。

## 2.1 データモデル

現行システムはすべてのデータをGoogle Sheets/Driveに保持している。

| データ | 保存場所 | 備考 |
|---|---|---|
| 顧客情報 | `顧客DB_New` シート | ヘッダー名からの列検出方式(`顧客ID`/`氏名`/`住所`等) |
| 家族/世帯情報 | `家族DB_New` シート | 顧客CSVの自由記述欄をヒューリスティックに解析して生成 |
| スタッフ・認証情報 | Staffシート | ログインID・パスワードハッシュ・セッショントークンを同一シートの列に保持 |
| 予定/勤怠 | Google Calendarのタグ付きイベント + 出勤簿シート | `[予約確定]`等のタグで種別判定、氏名の文字列一致で顧客と紐付け |
| 日報・事故報告・領収書 | 専用シート + Driveフォルダ | Gemini APIでAIによる文章生成・OCRを実施 |

## 2.2 顧客データの自動取込(RESERVA連携)

`checkAndImportLatestCsv()` が、外部予約システムからエクスポートされるCSV(UTF-16LE・タブ区切り、29列)をDriveフォルダから検出し、`顧客DB_New`/`家族DB_New` の内容を**全置換**する仕組みになっている。これは、エクスポートが一部欠損していた場合に既存データを丸ごと消してしまうリスクを抱えている。この挙動は新システムでは踏襲しない(第6章)。

## 2.3 認証方式

メールアドレス+パスワードのカスタム認証で、パスワードは共有ソルト付きSHA-256、セッショントークンと有効期限はStaffシートの列に直接書き込まれる(7日ローリング延長)。この方式はテーブル/コレクションを分離した仕組みへ置き換える(第9章)。

## 2.4 まとめ

現行システムは「単一法人・単一Googleアカウントに強く依存した設計」であり、マルチテナント化・決済/カルテ機能の追加・法人ごとのデータ形式吸収のいずれも、現行アーキテクチャの延長では実現が難しい。以降、ゼロベースで技術構成を検討する。

# 3. データベース選定比較

「汎用的なリレーショナルDB」という方向性のもと、候補を比較する。

| 候補 | このシステムでの適合度 | 主な弱点 |
|---|---|---|
| **PostgreSQL(推奨)** | Row Level Security(RLS)を標準搭載しテナント分離に直接使える。`EXCLUDE USING gist` 制約でスタッフの二重予約を構造的に防止できる。生成列(GENERATED COLUMN)とdeferred constraint triggerで請求明細の合計不整合を防げる。JSONB型で法人ごとのカスタム項目を柔軟に持てる。本システムが要求する制約のほぼすべてをDBの機能だけで満たせる | コネクション管理・マイグレーション運用は自前で設計が必要(マネージドサービスの利用で軽減、第7章) |
| MySQL/MariaDB | 実績・知名度は高いが、RLSが標準搭載ではなくビュー等での代替実装が必要。範囲重複を防ぐ`EXCLUDE`制約に相当する機能がなく、二重予約防止をアプリ側ロックで自作する必要がある | マルチテナント分離・予約制約の実装コストがPostgreSQLより明確に高い |
| Cloud Spanner(Google) | 水平スケール・強整合性に優れるが、この規模(数社・数百レコード)には過剰性能。PostgreSQL互換モードもRLSや拡張機能に制限がある | 最小構成でもCloud SQLより運用コストが高く、小規模事業には不向き |
| CockroachDB | PostgreSQL互換の分散SQL。将来、地理分散が必要になった場合の選択肢になり得る | 現時点でその要件がなく、導入は運用の複雑さが増すだけ |
| SQL Server | エンタープライズでの実績はあるが、Linux/GCP中心の本構成とは相性が薄い | 採用する積極的な理由が見当たらない |

**結論**: PostgreSQLを推奨する。マルチテナントSaaSで予約・決済・記録系データを扱う場合の一般的なベストプラクティスであり、新規性のある選択ではなく、要件に対して手堅い選択である。

# 4. マルチテナント設計

## 4.1 テナント分離の方式

`tenant_id` を各テーブルの先頭複合キーとして持ち、Row Level Security(RLS)で強制する「shared schema」方式を採る。

```sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE customers FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON customers
  USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

複合主キー(`tenant_id, id`)+複合外部キーにより、A社の予約がB社の顧客を参照するような取り違えを**構造的に不可能**にする。

比較として「テナントごとにスキーマを分ける」「テナントごとにDBを分ける」方式もあるが、今回は採用しない。理由は、法人ごとにスキーマが分岐すると将来訪問看護向けの機能拡張時に法人ごとの差異が積み重なり、保守が破綻しやすいため。将来、特定の法人が物理的分離を要求した場合の「逃げ道」として、テナントごとに接続先DBを切り替えられる抽象化だけは最初から用意する。

## 4.2 将来の業種拡張(訪問看護)

業種ごとにスキーマを分岐させず、以下の3つの仕組みで吸収する。

- **共通テーブルの追加**: `care_records`(共通)に対し、訪問看護固有の`nursing_vitals`(バイタル)や`physician_instructions`(指示書)を追加。ベビーシッター業のテナントではレコードが単に存在しないだけ。
- **テナント別カスタムフィールド**: 表示・検索用途に限定したJSONB列(`custom_fields`)。請求・カルテの本体データはここに置かない。
- **機能フラグ**: `tenant_features` テーブルで、テナントごとに使う機能を有効化・無効化する。

# 5. 予約管理

```sql
reservations(tenant_id, id, customer_id, service_item_id, status,
             scheduled_start, scheduled_end, business_date, address_id, is_online, ...)
reservation_assignments(tenant_id, id, reservation_id, staff_id, period, status)
visits(tenant_id, id, reservation_id, staff_id, actual_start, actual_end, status)
```

「予定(reservations)」と「実績(visits)」を分離する。現行システムはGoogle Calendarの予定と出勤簿を氏名の文字列一致で結び付けており、表記ゆれで顧客が正しく紐付かないリスクがある。新システムでは`external_ids`テーブルで外部システムのIDと内部IDを明示的に対応付ける。

スタッフの二重予約は、PostgreSQLの排他制約で構造的に防止する。

```sql
CREATE EXTENSION btree_gist;
ALTER TABLE reservation_assignments
  ADD CONSTRAINT no_staff_double_booking
  EXCLUDE USING gist (tenant_id WITH =, staff_id WITH =, period WITH &&)
  WHERE (status <> 'cancelled');
```

# 6. 請求・決済(settlement)

```sql
invoices(tenant_id, id, customer_id, invoice_no, status, subtotal_yen, tax_yen, total_yen, ...)
invoice_lines(tenant_id, id, invoice_id, line_no, quantity, unit_price_yen, tax_rate,
              amount_yen GENERATED ALWAYS AS (round(quantity * unit_price_yen)) STORED)
payments(tenant_id, id, customer_id, amount_yen, method, ...)
payment_allocations(tenant_id, id, payment_id, invoice_id, amount_yen)
```

金額は常に整数(銭単位)で保持し、浮動小数は使わない。明細合計と請求書ヘッダーの不整合を防ぐため、明細の金額は生成列(計算結果をDBが保証)とし、ヘッダーの合計値はdeferred constraint triggerでコミット時に検証する。支払いの過剰割当も同様の仕組みで防止する。

なお、医療保険・介護保険のレセプト請求(訪問看護特有の請求フォーマット)は、規制対応が別途必要な専門領域のため、**本フェーズのスコープには含めない**。自費/利用者負担分の請求機能までを対象とする。

# 7. カルテ・記録機能

```sql
care_records(tenant_id, id, customer_id, record_type, status, author_staff_id,
             body_internal, body_for_family, body_structured jsonb,
             ai_generated bool, ai_model, retain_until, ...)
care_record_revisions(id, tenant_id, care_record_id, revision, snapshot jsonb, changed_by, changed_at)
```

記録が「確定(submitted/signed)」後は内容を直接書き換えられないようDB権限とトリガーで強制し(`REVOKE UPDATE, DELETE`)、修正は必ず改訂レコードの追加(amends)として扱う。AIが生成した記録は、モデル名・プロンプトのバージョン・人間による確認済みかどうかを記録に残す(将来、訪問看護記録として扱われた場合の説明責任のため)。

保存年限はテナントごとの設定値とし、コード側にハードコードしない。訪問看護記録の法定保存年数は事業者の顧問・社労士等に確認の上、設定する(第14章の要確認事項)。

# 8. プラガブルなデータ取込層

各法人が持つ既存データ(CSV、Excel、外部予約システムのエクスポート等)を、コード変更なしで取り込めるようにする。

```
取込 → デコード → パース → マッピング → 検証/差分表示 → 人間によるレビュー → 適用
```

- **設定駆動のフィールドマッピング**: 列名のエイリアス、日付/金額等の変換ルールをテナントごとの設定として保存。新しい法人のCSV形式が既存の変換関数で対応できる場合、**コード変更は不要**。
- **アダプタレジストリ**: 取込元の「プロトコル」自体が特殊な場合(外部システムのAPI連携等)のみ、新しいアダプタをコードとして追加する。既存の全法人に影響を与えない追加的な変更に留める。
- **共有変換ライブラリ**: 現行の`parseFamilyInfo`(世帯情報の解析)や日付の和暦処理など、実際の運用で磨かれたロジックは資産として残し、テナント非依存の変換関数として移植する。
- **危険な全置換の廃止**: 現行の「取込データで既存データを丸ごと置き換える」処理は廃止し、差分適用+ソフトデリート(消えたのではなく「取込元に存在しない」フラグを立てる)に変更する。想定外の欠損データが人手でレビューされるまで自動適用しない安全装置(閾値超えでブロック)を設ける。

# 9. GAS+Sheetsからの移行計画

ビッグバン移行は避け、機能単位で段階的に移行する。各フェーズは「新システムが実データで旧システムと一致することを確認できてから」次に進む。

| フェーズ | 内容 |
|---|---|
| 0. 基盤構築 | GCPプロジェクト・DBスキーマ・CI環境を用意。ユーザーには見えない準備段階 |
| 1. 認証移行 | スタッフをID管理サービスへ移行。既存のパスワードハッシュ方式は移行できないため、パスワード再設定を依頼する |
| 2. 顧客/家族データ移行 | 新しい取込パイプラインでCSVを新DBへ投入。旧システムへの書き込みは並行して継続し、影響を最小化 |
| 3. 日報・事故報告・領収書 | 追記型のデータのため移行リスクが低く、優先的に新システムへ切り替え |
| 4. 予約・スケジュール | Google Calendarを当面正としつつ、新システムに複製。十分な検証後に新システム側を正とする |
| 5. 勤怠 | 最も慎重に扱う(給与計算に直結)。既存の勤怠計算ロジックとの数値一致を検証してから切替 |
| 6. 請求・カルテ | 新規機能のため移行対象データがなく、次のテナント獲得に向けて本格構築 |
| 7. 旧システムの停止 | 各GASプロジェクトに残る手動設定のトリガー(`gas-root-serach`の`main()`等)を明示的に洗い出し、廃止する |

# 10. ホスティング・運用構成

## 10.1 実行基盤: GCP(Cloud Run)

Google Calendar・Google Maps・Gemini APIとの連携がすべてGoogle系であるため、実行基盤もGCPに統合する。TypeScript/Hono/Drizzle ORM/ローカルSQLite開発というスタックはCloud Run上でもそのまま活用でき、コードの移植性は損なわれない。DNS/CDN/WAFとしてCloudflareを前段に置くことは後日いつでも可能なため、まずはGCP単一構成とする。

## 10.2 既存GASトリガーとの対応

| 現行(GAS) | 新システム |
|---|---|
| CSV自動取込のポーリング | GCSイベント駆動、または定期実行(Cloud Scheduler) |
| 深夜の全スタッフ勤怠同期(1回の実行に6分制限) | スタッフごとにタスクを分割(Cloud Tasks)し、制限を回避 |
| ルート検索・LINE WORKS通知 | 同上+Cloud Tasksによる再送・流量制御 |
| ログのバッファリング→Drive CSV | Cloud Loggingへ直接出力 |

## 10.3 Google Maps APIの移行に関する注意

2025年3月の制度変更により、**新規のGCPプロジェクトではDirections API/Distance Matrix API(レガシー)を新たに有効化できない**。新システムはRoutes API(後継API)を前提に設計する必要があり、現行`RouteSearch.js`のAPI呼び出し部分は移植(書き換え)が発生する。

## 10.4 認証サービス

Firebase Auth(またはGCP Identity Platform)のメール+パスワード認証を利用する。5万MAUまで無料であり、本規模では実質コストが発生しない。

# 11. コスト感(PoC重視の段階プラン)

「PoCにはあまり予算をかけたくない」という要望を踏まえ、DBのホスト先をフェーズごとに変える。

| フェーズ | 実行基盤 | データベース | 月額の目安 |
|---|---|---|---|
| 開発 | ローカル | SQLite | ¥0 |
| PoC(テストデータ限定) | Cloud Run(`min-instances: 0`) | **Neon または Supabase の無料プラン**(いずれもPostgres。比較は11.2節) | **ほぼ¥0** |
| 本番(実顧客データ投入後) | Cloud Run | **Cloud SQL for PostgreSQL(東京リージョン)** | 非HA構成: 概算¥5,000〜7,000/月、HA構成: 概算¥10,000〜14,000/月 |

## 11.1 サービス別の無料枠(この規模での目安)

| サービス | 目安 |
|---|---|
| Cloud Run | 無料枠内で収まる見込み(`min-instances: 0`時) |
| Secret Manager | 無料枠内 |
| Cloud Scheduler / Cloud Tasks | 無料枠内 |
| Firebase Auth(メール+パスワード) | 5万MAUまで無料 |
| Firebase Hosting / FCM | 無料枠内・FCMは無料 |
| **Cloud SQL for PostgreSQL** | **唯一、停止してもストレージ課金が残る固定費コンポーネント** |

コストドライバーは実質Cloud SQLのみ、という調査結果になる。そのため、PoC期はNeonまたはSupabaseの無料枠を使い、実データを扱う本番段階でのみCloud SQL(東京リージョン)へ切り替えるのが最も合理的である。どちらを使うかの判断基準は11.2節で述べる。

## 11.2 PoC用DBホスティングの選択: Neon vs Supabase

PoC段階のDBホスティングはNeon・Supabaseのいずれも無料枠で要件を満たせるため、本書では一方に決め切らず、判断基準を示した上で2択として提示する(以下は2026年8月時点の調査)。

| 観点 | Supabase | Neon |
|---|---|---|
| 無料枠 | DB 500MB、ファイル1GB、egress 5GB、MAU 5万、org当り無料プロジェクト2つ、バックアップ無し | 0.5GB/プロジェクト、100 CU時間/月、プロジェクト数上限は多め(最大100) |
| 東京リージョン | `ap-northeast-1`(東京)が無料枠から選択可能(他にSingapore/Seoul/Sydney等) | 無し。最寄りはAWS `ap-southeast-1`(シンガポール) |
| 休止時の挙動 | 7日間DBアクセス無しで一時停止(ダッシュボード閲覧はカウントされない、実際のクエリが必要)。復帰には手動「Restore」操作が必要。長期間放置すると自動的に完全削除され、復旧不可になるリスクがある | 真のスケールトゥゼロ。数秒で自動停止・次のクエリで自動的かつ透過的に復帰。非活動による削除リスクなし |
| ロックイン | PostgREST・Supabase Auth・Realtimeを使わず素のPostgres接続(独自APIレイヤー経由)で使えば低リスク。未使用のSupabase管理スキーマ/ロール(auth, storage, realtime, anon, authenticated等)は無害に残るだけ | ほぼゼロ。素のPostgres+ブランチ機能のみで独自機能への依存がほぼ無い |
| Cloud SQLへの移行 | 実質pg_dump/pg_restoreで可能。ただしSupabase管理スキーマ・ロールの除外が必要(機械的な作業、書き直しではない) | 同様にpg_dump/pg_restoreでほぼクリーン、Neon固有のノイズはほぼ無い |
| 無料枠超過後の料金 | Pro: $25/月(コンピュート込みの固定額) | 使用量課金・最低料金なし。低頻度・断続的なPoC利用なら一般にNeonの方が安くなりやすい |
| 2025-2026の動向 | 大きな無料枠縮小等の変更は見当たらない。2025年に軽微な障害報告はあるが概ね安定 | 2025年5月にDatabricksに買収。買収後、料金はむしろ改善(コンピュート15-25%減、ストレージ約80%減、無料枠のCPU時間が2倍、$5/月の最低料金を撤廃)。一部Azureリージョンは2026年4月に新規作成不可に(既存プロジェクトは継続) |

**判断基準**:

- **Supabaseを選ぶ場合**: 東京リージョンを最初から使えるため、越境データ移転の論点が発生せず、本番のCloud SQL(東京)への移行が「同一リージョン内の載せ替え」で済む。ただし無料枠が7日間非アクティブで一時停止し、長期放置で自動削除されるリスクがあるため、PoC中も定期アクセスやpg_dumpでのバックアップ運用が必要。
- **Neonを選ぶ場合**: 真のスケールトゥゼロで運用が楽(削除リスクなし、自動復帰)、低頻度利用なら料金も安くなりやすい。ただし東京リージョンが無く、シンガポールでのデータ保管となるため、実データ投入前にCloud SQL(東京)へ移行する運用ルールが必須。

どちらも「素のPostgres接続で使えばロックインは低い」という点は共通であり、DB選定そのものが移行の障害になることはない。最終的な選定はPoC開始時点で決定する(第14章)。

## 11.3 AI・API利用料に関する留意事項

- Gemini API(現行`GEMINI_MODEL_REPORT`/`GEMINI_MODEL_OCR`で利用中のモデル)は、将来的なモデル世代交代・料金改定の可能性がある。モデル名を環境変数/設定で切替可能にする現行の設計方針を、新システムでも維持する。
- Google Maps Routes APIは月間無料コール数の範囲内で収まる見込みだが、既存のAPI呼び出しコードの移植(前述10.3)が必要。

**注記**: 本章の金額はすべて2026年8月時点の調査(WebSearch経由の二次情報が中心)による概算であり、特にCloud SQLの東京リージョン単価・Gemini API・Google Maps APIの無料枠については確度が低い部分がある。**発注・契約前に必ずGCP公式の料金計算ツール等で最終確認すること。**

# 12. 将来検討: ネイティブアプリ化(React Native)とジオフェンス

スタッフの訪問先への到着・退出を正確に検知したい(ジオフェンス)という将来要望を踏まえ、React Nativeによるネイティブアプリ化を検討する。結論として**React Nativeは妥当な選択**であり、認証・データベースのアーキテクチャは変更不要だが、ジオフェンスの信頼性確保とオフライン同期の仕組みが新たに必要になる。

## 12.1 ジオフェンスライブラリの比較

| 選択肢 | 特徴 | 評価 |
|---|---|---|
| Expo `expo-location` + `expo-task-manager` | Expo管理下(EAS Build、Expo Goでは非対応)で追加コード不要で使える無料の標準機能 | iOSは20件までの同時監視region制限あり。**Androidはアプリが完全終了(kill)された状態からの自動復帰がされない**、および誤発火の報告が複数ある。信頼性を業務要件とするには不安が残る |
| `react-native-background-geolocation`(Transistorsoft) | 現場サービス系アプリで広く使われる商用ライブラリ。モーション検知と連動した省電力ジオフェンス。Expo Config Pluginがあり、EAS Build経由でExpo管理下でも導入可能(Expo Goは不可) | **両OSで最も信頼性が高いとされる商用の定番**。ネイティブSDK部分は有償ライセンス(本番リリースビルドには購入が必要)。**具体的な現在の価格は本書執筆時点で確認できておらず、導入判断前に販売元へ直接確認が必要** |

**結論**: PoC/デモ段階はExpo標準機能で試作し、業務として本格導入する段階でTransistorsoft社の商用ライブラリへの切替を検討する、という段階的な進め方を推奨する。

## 12.2 OS側の制約

- **iOS**: 「常に許可」(Always)の位置情報権限を要求するには、Info.plistに具体的な利用目的の文言(`NSLocationAlwaysAndWhenInUseUsageDescription`)が必須で、審査で弾かれやすい。iOS 13以降は「使用中のみ許可」→ 後から「常に許可」への2段階フローが必要。加えて2024年5月以降、位置情報APIを使うサードパーティSDK(ジオフェンスライブラリ本体も対象)には「プライバシーマニフェスト」の添付が求められる。
- **Android**: メーカー(Samsung、Xiaomiなど)ごとに独自のバックグラウンドアプリ制限・電池最適化があり、フォアグラウンドサービス(通知常時表示)+バッテリー最適化除外のユーザー許可を組み合わせても**OS標準機能だけでは完全に防げない**。現場スタッフへの端末設定案内(ホワイトリスト登録等)が運用上必要になる。

## 12.3 認証・データベースへの影響

- **認証**: 変更不要。Web版と同じFirebase Auth/Identity Platformを使うが、React Native向けは`@react-native-firebase/auth`(ネイティブSDKをブリッジする方式)を用いるのが標準。トークンの保存は`expo-secure-store`(iOS Keychain/Android Keystoreを利用)で行う。
- **データベース**: 変更不要。PostgreSQLはサーバー側のみに存在し、ネイティブアプリもWebと同じくHono API経由でアクセスする。
- **新たに必要な仕組み(オフライン同期)**: 訪問先での電波不安定に備え、ジオフェンスのIN/OUTイベントや訪問チェックイン/アウトを端末内に一時保存し、通信回復時にサーバーへ同期する仕組みが必要。`expo-sqlite`(端末内の軽量SQL)に「未送信(pending)/送信済み(synced)」の状態を持つ小さな送信待ちテーブル(outboxパターン)を持たせるのが2026年時点での標準的な実装方法。より本格的な同期プロトコルが欲しい場合はWatermelonDBという選択肢もある。
- **プッシュ通知**: 認証にRNFirebaseを使う前提と揃え、`@react-native-firebase/messaging`を使用する(Expo標準の通知機能と混在させると不具合が出るとの報告があるため、片方に統一する)。

# 13. PoC: クライアント側のみで動くダミーデータデモの実現性

「まずはダミーデータを生成し、ローカルのSQLite的なものだけで、遠隔のパートナー企業に触ってもらう」という進め方の実現性について検討する。

## 13.1 結論

**UI/機能の方向性についてのフィードバックを得る「クリックできる試作品」としては現実的**。ただし、これは第11章で述べたPoC(Neon/Supabase Postgres + Cloud Run)の**前段**に位置づけるべきものであり、それを代替するものではない。

| 段階 | 内容 | 目的 |
|---|---|---|
| **Phase -1(新設): クリック試作品** | サーバー無し。ブラウザ内のみで動作。ダミーデータを起動時に生成 | UI/UX・機能範囲そのものについて、最速・最安でパートナー企業のフィードバックを得る |
| Phase 0: PoC(第11章の既存プラン) | Cloud Run + Neon/Supabase Postgres(無料枠) | 実際のAPI・DBを介した業務フローの動作確認 |
| 本番 | Cloud Run + Cloud SQL(東京) | 実顧客データの本番運用 |

## 13.2 技術的な実現方法

- **ブラウザ内DB**: `PGlite`(ElectricSQL社)を推奨。SQLiteではなく**本物のPostgreSQLをWebAssemblyにコンパイルしたもの**で、本番と同じSQL・スキーマがそのまま動く。ただし2026年8月時点でまだ1.0未満(アルファ〜ベータ)であり、データの永続性を保証しないという注記がある。捨てても構わないデモ用データを扱う本用途では問題にならない。
- **ダミーデータ生成**: `@faker-js/faker`の日本語ロケール(`fakerJA`)で氏名・住所・電話番号等を生成可能。ただし**漢字氏名にふりがなを自動で付与する機能は標準では無い**ため、カルテ等でふりがな表示が必要な画面では別途工夫が必要。
- **配置場所**: サーバー不要の静的サイトとして、Cloudflare PagesまたはGitHub Pagesに置くのが最も無料枠に収まりやすい(Vercelの無料枠は商用利用が規約上不明確なため今回は避ける)。

## 13.3 事前に伝えておくべき限界

- **パートナー企業同士・同一企業の複数人でのデータ共有はできない**。各人のブラウザ内に独立したデータが生成されるだけで、Web版の「管理者が入れた予約をスタッフが見る」といった連携の確認はできない。
- **データが消える可能性がある**。特にiOS Safariは、7日間操作がないブラウザ上のデータを自動的に消去する仕様があり、パートナー企業が数日空けて再度開くとデータが消えていることがある。「デモ用データであり保存を保証しない」旨をあらかじめ伝える。
- **同時に2つのタブを開くと不整合が起きうる**ため、対策(タブ間の排他制御)を組み込むか、「1タブのみで利用してください」と案内する。
- **本番の並行処理・マルチテナント分離(RLS)の検証はできない**。UIの動作確認に徹する。
- 初回アクセス時にWASMのダウンロード・初期化で数秒待たせる可能性がある。

## 13.4 まとめ

「ダミーデータ+ブラウザ内DB」でのパートナー企業向けデモは、コストほぼゼロ・構築も速いため、**まず着手する価値がある**。ただし「実際の業務フローが動くことの検証」ではなく「画面・機能の方向性のフィードバックを得るためのもの」と明確に位置づけ、パートナー企業にもその前提を伝えることが重要。
