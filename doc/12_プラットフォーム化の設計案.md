# 12 プラットフォーム化の設計案(提案・未決定)

- 目的: katahimo-app を「キューテスト様専用の子育て訪問アプリ」から「訪問介護・訪問看護・家事代行・子育て訪問などを扱う訪問サービスのプラットフォーム」にする方法の検討。
- 対象読者: 方針を決める人、次の開発の担当。
- 状態: **提案**。コードはまだ変えていない。実稼働前なので、互換性(DB・API・画面)は考えない前提。

## 1. 結論

**katahimo-app を作り替えるのではなく、`katahimo-dev/carevisit` を唯一のプラットフォームとし、katahimo-app の機能をモジュールとして carevisit に移す。** katahimo-app は凍結し、GAS版と同じく「業務ロジックの仕様」として参照する。

### 1.1 理由

| 観点 | carevisit | katahimo-app |
| --- | --- | --- |
| 前提 | 最初から多業種のマルチテナント SaaS(シッター / 訪問介護 / 訪問看護・リハ) | 1社(キューテスト様)の GAS アプリの置き換え |
| 業種差分の仕組み | 業種プリセット(`core/src/domain/presets.ts`)と機能モジュール(`kernel` の `defineModule`、`platform.tenant_modules`) | `platform.tenants.business_type`・`tenant_features`・`custom_field_definitions` は表だけで、使うコードがない |
| 組織 | 拠点(`offices`)あり | 拠点なし |
| 認証 | Identity Platform(招待制・管理職は MFA 必須)。パスワードを持たない | 自前の argon2 とパスワード再設定 |
| 割当て | Route Optimization API での提案・手直し・確定・再最適化、打刻、効果測定は実装済み | 表だけ(doc/10、未実装) |
| 業種に依存する部分 | ほぼ無し | 出勤簿の列記号、RESERVA、教育思考★・PSI、GAS Bridge、子ども前提の報告の本文 |
| 予定 | 2026-10-24 に alca・フォールで稼働 | 未稼働 |

- carevisit の設計書(`docs/superpowers/specs/2026-10-03-carevisit-mvp-design.md` §1.4)にも、すでに「katahimo の子育て訪問の機能も、将来この基盤の上にモジュールとして作り直す」と書いてある。
- 技術の系統は同じ(TypeScript / Hono / Drizzle / PostgreSQL RLS / React / Cloud Run)。UoW・複合キー・FORCE RLS・zod 契約・監査ログの規則もほぼ同じなので、移植は「コピーして作り替える」で進められる。
- 基盤を2つ並べて育てると、認証・RLS・インフラ・CI・運用を二重に保守することになる。統合するなら、実稼働の前の今がいちばん安い。

### 1.2 もう一つの案(採らない)

katahimo-app を土台にして多業種化する案。

- 利点: 日報AI・出勤簿・領収書・outbox・Web Push・認証の強化など、機能はこちらの方が多い。
- 欠点: 拠点・モジュール機構・プリセット・割当ての最適化・Identity Platform を作り直す必要がある。どれも carevisit にはすでにある。出勤簿の列記号・GAS 一致テスト・RESERVA・GAS Bridge など、GAS 由来の形がコアに入り込んでいて、剥がす量も多い。
- carevisit 側の 10/24 稼働を止めない限り、結局どちらかを捨てることになる。

## 2. プラットフォームの設計原則

業種の違いは「**コードの分岐**」ではなく、次の4層で表す。

| 層 | 中身 | 変える人 | 例 |
| --- | --- | --- | --- |
| 1. コア | テナント・拠点・スタッフ・利用者・サービス対象者・訪問・割当て・監査・認証 | 開発 | 全業種で同じ |
| 2. 機能モジュール | 記録・記録AI・勤務表・立替経費・通知・カレンダー連携・最適化・効果測定・(将来)介護保険請求 | 開発 | `records`、`timesheet` |
| 3. 業種パック(プリセットの拡張) | 用語・資格・サービス種別・記録のひな形・評価尺度・既定のモジュールと設定。**コードではなくデータ** | 開発(データとして) | `sitter`、`home_care`、`home_nursing`、`childcare_visit` |
| 4. テナントの設定 | モジュールの有効化と設定、ひな形の上書き、独自項目、出力テンプレート | テナント管理者 / 運用担当 | キューテスト様の出勤簿の Excel ひな形 |

規則:

- 業務ロジックを `if (preset === 'home_care')` で分けない。分けたくなったら、その違いを業種パックのデータ(設定値・ひな形・ルール)として表せないかを先に考える。
- **制度に従う計算**(介護保険の単位数・加算・国保連の伝送、医療保険の訪問看護)だけは例外とし、業種専用のモジュールに閉じ込める。コアや他モジュールには持ち込まない。
- 業種パックは版付きにする(`preset_version`)。テナント作成時に写して、以後はテナント側で上書きする。パックを更新しても既存テナントは自動では変わらない。
- 1社の固有物(RESERVA の CSV、キューテスト様の出勤簿の列、GAS)は「テナントの設定」または「取り込みの対応表」に置く。コアにもモジュールにも名前を出さない。

## 3. コアのドメインモデル(carevisit の core を広げる)

carevisit の core(`offices`、`staff`、`clients`、`visit_requests`、`visit_recurrences`、`schedule_assignments` など)に、次の汎用化を加える。

### 3.1 契約者とサービス対象者を分ける

| 概念 | 子育て訪問・シッター | 訪問介護・訪問看護 | 家事代行 |
| --- | --- | --- | --- |
| `clients`(契約・請求・住所・連絡先の単位) | 世帯(保護者) | 利用者本人(または家族) | 世帯 |
| `care_recipients`(サービスを受ける人。0..n) | 子ども | 利用者本人(1人) | 無し(0人) |
| `client_contacts`(連絡先・緊急連絡先・キーパーソン) | 保護者 | 家族・ケアマネジャー | 本人 |

- katahimo-app の `customers` + `care_recipients`(子ども)と同じ形を、業種によらない名前で持つ。介護では「利用者 = 対象者」の1件を自動で作る。
- 対象者の属性(生年月日・アレルギー・要介護度・主治医など)は、型付きの共通列(生年月日など)と、業種パックが定義する項目(後述 §4.1 のひな形と同じ仕組み)に分ける。

### 3.2 サービス種別(service catalog)

`service_types`(テナントごと。業種パックから写す): コード・名前・既定の所要時間・必要な資格・同時に入るスタッフ数・料金の単位・記録のひな形(どの記録を書くか)。

- 例: シッター「ベビーシッター 120 分」、訪問介護「身体介護 1(20〜30 分)」「生活援助 2」、訪問看護「訪問看護 I-2」、家事代行「定期清掃」。
- 訪問(`visit_requests`)は `service_type_id` を持ち、所要時間・資格・書く記録はここから決める。carevisit の今の「プリセットの既定の所要時間」はこの表へ移る。

### 3.3 訪問の一生

依頼(`visit_requests` / 定期パターン) → 割当て(`schedule_assignments`。最適化または手入力) → 現場(`fld_visit_events` の打刻) → 記録(`records`) → 確認・承認 → 締め(勤務表・立替経費・将来の請求)。

- ドメインイベント(`visit.completed`、`record.submitted`、`period.closed` など)で次のモジュールへ渡す。モジュール同士は互いの表を読まない(carevisit §3.2 の規則のまま)。
- katahimo-app の「Google Calendar の予定から出勤簿を作る」流れは、カレンダーを**予定の入口の1つ**(`calendar-sync` モジュール)にして、作る先を `visit_requests` / `schedule_assignments` に揃える。出勤簿はカレンダーではなく確定した割当てと打刻から作る。

### 3.4 権限

- carevisit の「ロール(`staff` / `office` / `admin`)+ モジュールごとの権限宣言」を続ける。役割を業種ごとに増やさない。
- 足すもの: **拠点の範囲**(事務所の人は自分の拠点だけ)と、**要配慮個人情報の項目の閲覧権限**(看護記録・病歴などは権限 `records.sensitive.read` を持つ人だけ。閲覧は必ず監査ログに残す)。
- katahimo-app の「他人の記録の閲覧はログに残す」「staff の id はセッションから決める」の規則はそのまま移す。

## 4. 機能モジュール(katahimo-app からの移植の対応)

| モジュール | 中身 | katahimo-app の出どころ | 汎用化のしかた |
| --- | --- | --- | --- |
| `records` | 訪問記録・事故報告・ヒヤリハット・申し送り。改版履歴・保存期限・締め後の編集禁止 | `care_records` / `care_record_revisions` / 0004 のガードトリガー、`reports/*` | 本文を**記録のひな形**で定義する(§4.1)。日報の「社内向け / 保護者向け」も、ひな形の項目と公開範囲で表す |
| `record-ai` | 記録の下書き生成。生成ログ・利用語の集計 | `reportAi.ts`、`promptAssembly.ts`、`report_*` マスタ | 「年齢帯 × 教育思考★ × PSI」を、**条件付きの語句マスタ**と**評価尺度**の組み合わせに一般化(§4.2) |
| `timesheet`(勤務表) | 訪問・移動・事務作業から勤務時間・移動距離を作る。月の締め。Excel 出力 | `attendance_*`、`attendanceCalc.ts`、`sheetTemplate.ts`、`attendanceWorkbook.ts` | 元データは打刻と割当て。列記号は**テナントごとの出力テンプレート**(§4.3)に閉じ込め、キューテスト様の出勤簿はその1件にする |
| `expenses`(立替経費) | 領収書の画像・重複検出・論理取消・会社負担・締め | `receipts` / `receipt_uploads`、`receiptDedupe.ts`、`receiptCancel.ts` | ほぼそのまま。取消の期限は設定値にする |
| `notifications` | Web Push・メール・Google Chat の通知。翌日の予定・アラート | `push_subscriptions`、`web-push`、`notificationText.ts`、outbox | 通知の種類をモジュールが登録する。アラートの条件(PSI ≤ 2 など)は評価尺度の側に持つ |
| `calendar-sync` | Google Calendar を予定の入口にする(最適化を使わないテナント向け) | `google-schedule`、`calendarSources.ts`、`calendarPolicy.ts` | 取り込んだ予定は `visit_requests` / 割当てにする。タイトルの書き方の規約はテナント設定 |
| `csv-import`(既存) | 利用者・スタッフ・訪問の取り込み | `reservaCsv/`、`staffMasterCsv/` | RESERVA の列は carevisit の「列の対応表」の既定の1つにする。外部 ingest API(`POST /api/integrations/customers`)もここへ |
| `optimization` / `field` / `measurement`(既存) | 割当ての最適化・打刻・効果測定 | doc/10 の構想 | carevisit の実装を使う。doc/10 は破棄 |
| (将来)`care-plan` | 訪問介護計画書・手順書・サービス提供責任者の確認 | 無し | 記録のひな形と同じ仕組みで計画書を作る |
| (将来)`ltc-billing` | 介護保険の実績・単位数・加算・国保連の伝送 | 無し | `home_care` 専用。§2 の例外 |
| (将来)`family-portal` | 家族が記録(公開範囲が家族の項目)を見る | 日報の保護者向け文 | `records` の公開範囲を使う |

移さないもの: GAS Bridge とスプレッドシートへのミラー、GAS シートの取り込み(`legacy-sheets`)、GAS 一致テスト、GAS のパスワードハッシュ、`doc/partner/`。キューテスト様が GAS から移るための作業は、§6 のとおり CSV の取り込みで行う。

### 4.1 記録のひな形(record templates)

業種差のいちばん大きい「記録の中身」を、コードではなくデータで定義する。

- `rec_templates`(コード・名前・対象: 訪問 / 事故 / 対象者)と `rec_template_versions`(項目の定義 JSON・公開範囲・必須・入力の型・選択肢・要配慮の印・評価尺度の参照)。公開した版は変えない。
- `rec_records` は `template_version_id` と `body jsonb` を持ち、保存時にその版の定義で検証する。版付きなので、ひな形を変えても過去の記録は読める。
- 検索・集計・アラートに使う値は、型付きの表に取り出す: `rec_scale_values(record_id, scale_code, value)`。PSI のような値はここに入り、一覧の絞り込み・通知の条件・CSV に使う。
- 業種パックの既定: 子育て訪問「日報(社内向け・保護者向け・PSI・ES)」「事故報告」、訪問介護「サービス提供記録(バイタル・身体介護/生活援助の実施項目・特記事項)」「ヒヤリハット」、訪問看護「看護記録(SOAP・バイタル・処置)」、家事代行「作業報告」。
- 画面はひな形の定義から入力欄を組み立てる(項目の型は文字・長文・数値・時刻・選択・複数選択・評価尺度・チェック表・写真に限る)。自由度を上げすぎない。

### 4.2 記録AI の一般化

katahimo-app の「子どもの年齢帯 × 家庭の教育思考★ × PSI で語句を絞る」を、次の3つの組み合わせにする。

- **評価尺度**(`assessment_scales`): 段階・名前・説明。PSI(1〜5)、教育思考★(1〜5)、要介護度、ADL などを同じ表で持つ。値は対象者・世帯・記録のどれかに付く。
- **条件付き語句マスタ**(`ai_phrase_entries`): 語句・種類・条件(対象者の年齢の範囲、尺度の値の範囲、サービス種別)・並び順。今の `report_keywords` / `report_phrases` / `report_age_bands` はこの1つにまとまる。
- **調整ルール**(`ai_adjust_rules`): 「PSI が 3 なら教育思考を1段下げ、専門用語を禁止」のような規則。katahimo-app の `applyPsi` はコードに書いた規則だったが、子育て訪問の業種パックのデータにする。ルールの書ける形(条件 → 尺度の補正 / 語句の種類の禁止 / 警告の追加)はコードで決め、中身はデータ。

プロンプトのひな形(`{placeholder}` と `{#section}…{/section}`)、生成ログ(`report_ai_generations`)、記録への紐づけ、保存期間、Gemini のキーの秘密箱はそのまま移す。

### 4.3 出力テンプレート(Excel など)

- `export_templates`(テナントごと): 出力の種類(勤務表・記録一覧・経費)、列の定義(見出し・元の値・書式・Excel の式)、シートの名前の規則。
- katahimo-app の `sheetTemplate.ts`(列・式・キャッシュ値)は、この定義の1件「キューテスト様の出勤簿」に変える。式の検算テスト(`testFormulaEvaluator.ts`、LibreOffice のテスト)は「テンプレートの定義に対する一般のテスト」として移す。
- 計算の正はドメイン(勤務時間・移動距離)。Excel の式は表示のための写しで、キャッシュ値はドメインの値から入れる(今と同じ)。

## 5. DB の方針

- carevisit の規則をそのまま使う: 1 スキーマ + `tenant_id` + FORCE RLS、`(tenant_id, id)` の複合キー、UUIDv7、`row_version`、モジュールの表は接頭辞(`rec_`、`ai_`、`ts_`、`exp_`、`ntf_`、`cal_`)、マイグレーションは `packages/db` の1系列、カタログの検査で FORCE RLS と GRANT を確かめる。
- **型付きの列を基本にし、jsonb は「ひな形が定義する中身」だけ**にする。検索・集計・制約に使う値は必ず型付きの列か取り出し表に置く。
- `platform` に足す: `industry_packs`(パックのコードと版)、`tenants.preset` を `industry_pack_code` + `industry_pack_version` へ。テナント作成時にサービス種別・資格・ひな形・評価尺度・語句をテナントの表へ写す(`platform.provision_tenant()` の後の usecase)。
- katahimo-app から移す DB の仕組み: 締めのトリガー(締めた月の勤務・記録の変更禁止)、記録の改版履歴のトリガー、領収書の取消の列の固定、`entity_changes` の変更前の値、outbox(重複排除キー・リース・指数バックオフ・dead)、アプリのログのパーティション。carevisit にすでに同じ働きのもの(監査ログのパーティション、レート制限の関数)はそちらに揃える。
- 個人情報: 看護・介護では病歴・服薬などの要配慮個人情報が増える。ひな形の項目に「要配慮」の印を持たせ、API の応答で権限のない人には返さない。閲覧はログに残す。保存は CMEK(今と同じ。列の暗号化はしない)。

## 6. キューテスト様の移し方

carevisit 側でキューテスト様を `childcare_visit`(または `sitter` を広げた)業種パックのテナントにする。

1. 業種パック `childcare_visit` を作る: サービス種別、資格、記録のひな形(日報・事故報告)、評価尺度(PSI・ES・教育思考★)、AI の語句と調整ルール、出勤簿の出力テンプレート。
2. モジュール `records` → `record-ai` → `expenses` → `timesheet` → `notifications` → `calendar-sync` の順に移す。各モジュールに「katahimo-app と同じ結果になる」ことのテストを付ける(katahimo-app の GAS 一致テストと同じ考え方。比べる相手は katahimo-app の domain の関数)。
3. 取り込み: RESERVA の顧客 CSV を `csv-import` の対応表で、GAS 時代の日報・事故報告・領収書はいったん CSV に書き出して取り込む(GAS の API を直接読む作りは移さない)。
4. katahimo-app は凍結する(新しい機能は足さない)。doc/11 と同じ形の機能比較表を carevisit 側に作り、キューテスト様が使う機能が揃ったことを確かめてから切り替える。

## 8. 決めてほしいこと

1. **基盤を carevisit に一本化するか**(この案の前提)。一本化しない場合は、katahimo-app を土台にする案(§1.2)で設計し直す。
2. 1つのテナントで複数の業種(例: 訪問介護と家事代行を両方している会社)を扱うか。扱うなら、業種パックはテナントではなく**拠点またはサービス種別の単位**で持たせる。
3. キューテスト様の認証: katahimo-app の自前パスワードから Identity Platform(招待制)に移ってよいか。
4. 介護保険請求をこの基盤で作るか、既存の請求ソフトへ CSV で渡すか(作るなら最も大きいモジュールになる)。
5. 記録のひな形の編集をテナント管理者に開くか、運用担当だけにするか(開くと自由度は上がるが、AI の語句・アラート・出力テンプレートとの整合の検査が要る)。
