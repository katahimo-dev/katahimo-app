# 12 プラットフォーム化の設計案(提案)

- 目的: katahimo-app を「キューテスト様専用の子育て訪問アプリ」から「訪問介護・訪問看護・家事代行・子育て訪問などを扱う訪問サービスのプラットフォーム」にする方法の検討。
- 対象読者: 方針を決める人、次の開発の担当。
- 状態: **提案**。コードはまだ変えていない。katahimo-app は実稼働前なので、互換性(DB・API・画面)は考えない前提。

## 0. 決まったこと(2026-10-05)

| # | 項目 | 決定 |

## 1. 結論

**`katahimo-dev/carevisit` を唯一のプラットフォームとし、katahimo-app の機能をモジュールとして carevisit に移す。** katahimo-app は凍結し、GAS版と同じく「業務ロジックの仕様」として参照する。

| 観点 | carevisit | katahimo-app |
| --- | --- | --- |
| 前提 | 最初から多業種のマルチテナント SaaS(シッター / 訪問介護 / 訪問看護・リハ) | 1社の GAS アプリの置き換え |
| 業種差分の仕組み | 業種プリセット(`core/src/domain/presets.ts`)と機能モジュール(`kernel` の `defineModule`、`platform.tenant_modules`) | `business_type`・`tenant_features`・`custom_field_definitions` は表だけで、使うコードがない |
| 組織 | 拠点(`offices`)あり | 拠点なし |
| 認証 | Identity Platform(招待制・管理職は MFA 必須)。パスワードを持たない | 自前の argon2 とパスワード再設定 |
| 割当て | Route Optimization API での提案・手直し・確定・再最適化、打刻、効果測定は実装済み | 表だけ(doc/10、未実装) |
| 業種に依存する部分 | ほぼ無し | 出勤簿の列記号、RESERVA、教育思考★・PSI、GAS Bridge、子ども前提の報告の本文 |

- carevisit の設計書(`docs/superpowers/specs/2026-10-03-carevisit-mvp-design.md` §1.4)にも「katahimo の子育て訪問の機能も、将来この基盤の上にモジュールとして作り直す」とある。
- 技術の系統・規則(TypeScript / Hono / Drizzle / PostgreSQL RLS / React / Cloud Run、UoW・複合キー・FORCE RLS・zod 契約・監査ログ)はほぼ同じ。katahimo-app のドメインの関数とテストはほぼそのまま移せる。

### 1.1 katahimo-app の全機能は入るか

入る。carevisit のモジュール機構は「表・API・画面・権限・イベント」を1単位で足せる作りで、katahimo-app の機能はどれもこの形に収まる(§4 の対応表)。carevisit に**足りない基盤**は次の3つで、モジュールより先に移す。

| 足りないもの | 中身 | 出どころ |
| --- | --- | --- |
| 確実に届ける仕組み(outbox) | carevisit の EventBus はコミット後のプロセス内の呼び出しで、落ちると消える。メール・Web Push・Google Chat には再試行つきの outbox が要る | `outbox_messages`、`core/usecases/outboxWorker.ts`、`outboxDrainTrigger.ts`、`outbox-drain` ジョブ |
| テナントの秘密値 | テナントごとの Gemini のキー・Chat の Webhook を KMS で封をして持つ | `tenant_secrets`、`integrations/src/secret-box` |
| 締め・改版の DB の守り | 締めた月の勤務・記録を DB のトリガーで変更禁止、記録の改版履歴、領収書の取消の列の固定、変更前の値(`entity_changes`) | `0001_baseline_custom.sql`・`0004_defense_in_depth.sql` |

### 1.2 GAS版からのデータ移行はできるか

できる。katahimo-app に、そのために作った取込がすでにあり、carevisit の運用ジョブ(`ops`)に移す。

| データ | 取込の方法 | katahimo-app の出どころ |
| --- | --- | --- |
| スタッフ台帳(パスワードのハッシュを含む) | 台帳の CSV → スタッフ。パスワードは §5 のとおり Identity Platform へ | `ingestion/src/staffMasterCsv/`、`import:staff-master` |
| 顧客・家族(RESERVA の CSV) | `csv-import` の対応表「RESERVA」で取り込み、その後も10分ごとに自動 | `ingestion/src/reservaCsv/`、`csv-import` ジョブ |
| 日報・事故報告(全行) | Sheets API で直接読み、行番号で冪等に取り込む | `import:legacy-reports`、`ingestion/src/legacySheets/`、`legacy_imported_rows` |
| 領収書(一覧と Drive の画像) | Sheets API・Drive API で直接読み、Drive のファイルIDで冪等に取り込む | `import:legacy-receipts` |
| 当月の個別出勤簿 | 月のシートの CSV → 勤務の実体 | `import:attendance`、`ingestion/src/attendanceSheetCsv/` |
| AI のプロンプト・言葉の表 | 管理画面で貼り付け・xlsx 取込 | 🛠 管理 → 🤖 AI |

- どの取込も**何度流してもよい**作り。切替の前にリハーサルを繰り返し、切替日に最後の差分を流す。
- 取込は切替のための道具なので、業種パックや一般のモジュールではなく、キューテスト様のテナントで使う「移行用のジョブ」として置く(終わったら外せる)。
- スプレッドシートへの書き写し(GAS Bridge)は移さない(切替の後はアプリで完結)。シートで見ていた一覧・分析は、アプリの一覧・CSV・Excel と §8 の AI 分析で置き換える。

## 2. 業種差分の表し方

業種の違いは「**コードの分岐**」ではなく、次の4層で表す。

| 層 | 中身 | 変える人 | 例 |
| --- | --- | --- | --- |
| 1. コア | テナント・**事業**・拠点・スタッフ・利用者・サービス対象者・訪問・割当て・監査・認証 | 開発 | 全業種で同じ |
| 2. 機能モジュール | 記録・記録AI・勤務表・立替経費・通知・カレンダー連携・最適化・打刻・効果測定・(将来)介護保険請求 | 開発 | `records`、`timesheet` |
| 3. 業種パック | 用語・資格・サービス種別・記録のひな形・評価尺度・AI の語句と規則・既定の設定。**コードではなくデータ**。版付き | 開発(データとして) | `childcare_visit`、`housekeeping`、`home_care`、`home_nursing` |
| 4. テナントの設定 | モジュールの有効化と設定、ひな形・語句の編集、出力テンプレート、取込の対応表 | テナント管理者 / 運用担当 | キューテスト様の出勤簿の Excel の形 |

規則:

- 業務ロジックを `if (業種 === 'home_care')` で分けない。分けたくなったら、その違いを業種パックのデータ(設定値・ひな形・規則)で表せないかを先に考える。
- **制度に従う計算**(介護保険の単位数・加算・国保連への伝送、医療保険の訪問看護)だけは例外とし、業種専用のモジュールに閉じ込める。
- 業種パックは、事業を作るときにテナントの表へ**写す**。以後はテナント側で直す。パックを更新しても既存のテナントは自動では変わらない(差分を見て取り込む操作を用意する)。
- 1社だけの物(RESERVA の CSV の列、キューテスト様の出勤簿の列、GAS)は、テナントの設定か取込の対応表に置く。コードには名前を出さない。

### 2.1 1社で複数の業種(事業)

業種パックを「テナント」ではなく「**事業**(`business_lines`)」に付ける。

```
テナント(法人。例: キューテスト)
 ├─ 事業: 子育て訪問(業種パック childcare_visit)
 │    └─ サービス種別・記録のひな形・評価尺度・AI の語句
 └─ 事業: 家事代行(業種パック housekeeping)
      └─ サービス種別・記録のひな形
拠点・スタッフ・利用者(世帯)はテナントに1つずつ。事業をまたいで共有する
```

| 物 | 持つ単位 | 理由 |
| --- | --- | --- |
| スタッフ・資格 | テナント | 同じスタッフが両方の事業で働く。どの事業に入れるかは `staff_business_lines` |
| 利用者(世帯)・連絡先 | テナント | 同じ世帯がシッターと家事代行の両方を使う。契約は `client_contracts`(事業ごと) |
| サービス種別・記録のひな形・評価尺度・AI の語句 | 事業 | 業種で中身が違う |
| 訪問・割当て | テナント(訪問がサービス種別を通して事業を持つ) | 1人のスタッフの1日に、両方の事業の訪問が混ざる。移動・勤務時間・最適化はまとめて計算する |
| 勤務表・立替経費 | テナント(行に事業を持つ) | 給与・精算は法人単位。事業ごとの内訳も出せる |
| 用語(お客様 / 利用者) | 事業(画面はその訪問の事業の用語。事業をまたぐ画面はテナントの既定) | |
| モジュールの有効化 | テナント。事業ごとの設定は `business_line_module_settings` | 例: 記録AI は子育て訪問だけ |

carevisit の今の `tenants.preset`(1テナント1業種)は、この形に置き換える。

## 3. コアのドメインモデル(carevisit の core を広げる)

### 3.1 契約者とサービス対象者を分ける

| 概念 | 子育て訪問・シッター | 訪問介護・訪問看護 | 家事代行 |
| --- | --- | --- | --- |
| `clients`(契約・住所・連絡先の単位) | 世帯(保護者) | 利用者本人 | 世帯 |
| `care_recipients`(サービスを受ける人。0..n) | 子ども | 利用者本人(1人。自動で作る) | 無し |
| `client_contacts` | 保護者 | 家族・ケアマネジャー | 本人 |

対象者の属性は、型付きの共通列(生年月日など)と、業種パックが定義する項目(§4.1 のひな形と同じ仕組み。例: アレルギー、要介護度、主治医)に分ける。

### 3.2 サービス種別

`service_types`(事業ごと。業種パックから写す): コード・名前・既定の所要時間・必要な資格・同時に入るスタッフ数・料金の単位・書く記録のひな形。訪問(`visit_requests`)は `service_type_id` を持ち、所要時間・資格・記録はここから決まる。carevisit の今の「プリセットの既定の所要時間」はここへ移る。

### 3.3 訪問の一生と予定の入口

依頼 → 割当て(`schedule_assignments`) → 現場の打刻(`fld_visit_events`) → 記録 → 確認 → 締め(勤務表・立替経費・将来の請求)。モジュールの間はドメインイベント(`visit.completed`、`record.submitted`、`period.closed`)で渡し、互いの表は読まない(carevisit §3.2 のまま)。

予定の入口は2つ:

- **最適化**(carevisit の `optimization`): 訪問依頼から割当てを提案して確定する。
- **カレンダー連携**(`calendar-sync`、katahimo-app から): Google Calendar の予定を読んで割当てにする。キューテスト様は RESERVA → Google カレンダー → アプリの流れで回っているので、**この形を続ける**。GAS版と同じ規則(予定の題名の決まり・担当の決め方)をそのまま移す。

どちらの入口でも、勤務表(出勤簿)は**確定した割当てと打刻**から作る。katahimo-app の「カレンダーから直接出勤簿を作る」流れは、「カレンダー → 割当て → 出勤簿」に分ける。夜間の反映(22時)の結果は GAS版と同じにする(§6 の一致テスト)。

### 3.4 権限

- carevisit の「ロール(`staff` / `office` / `admin`)+ モジュールごとの権限宣言」を続ける。業種ごとにロールを増やさない。katahimo-app の `coordinator` は carevisit の `office` に当たる。
- 足すもの: **拠点・事業の範囲**(事務所の人は担当の拠点・事業だけ)、**要配慮個人情報の閲覧権限**(看護記録・病歴などは権限 `records.sensitive.read` を持つ人だけ。閲覧は必ず監査ログに残す)。
- katahimo-app の「staff の id はセッションから決める」「他人の記録を見たらログに残す」「これまでの記録は担当外の記録も見られる(引き継ぎのため。閲覧はログ)」はそのまま移す。

### 4.1 記録のひな形(テナント管理者が編集する)

業種差のいちばん大きい「記録の中身」を、コードではなくデータで定義する。

- `rec_templates`(事業ごと。コード・名前・対象: 訪問 / 事故 / 対象者)と `rec_template_versions`(項目の定義・公開範囲・必須・型・選択肢・要配慮の印・評価尺度の参照)。
- `rec_records` は `template_version_id` と `body jsonb` を持ち、保存のときその版の定義で検証する。版があるので、ひな形を直しても過去の記録は読める。
- 検索・集計・通知に使う値は型付きの表に取り出す: `rec_scale_values(record_id, scale_code, value)`。PSI はここに入り、一覧の絞り込み・アラート・CSV に使う。
- 項目の型は、文字・長文・数値・時刻・選択・複数選択・評価尺度・チェック表・写真に限る。画面は定義から入力欄を組み立てる。

**テナント管理者が編集するための守り:**

| 守り | 中身 |
| --- | --- |
| 下書き → 公開 | 編集は下書きの版に対して行い、公開した版は変えない。公開した版の記録はその版のまま |
| 消さずに隠す | 公開済みの項目は消せず「使わない」にする(過去の記録・CSV・AI の参照を壊さない)。型を変えたいときは別の項目として足す |
| 公開の前の検査 | 参照の切れを公開の前に止める: AI の語句・規則が使う評価尺度、アラートの条件、出力テンプレートの列、CSV の列、必須の項目(PSI など法人の決まり) |
| 試しの表示 | 下書きのまま、入力画面・保護者向けの表示・AI に渡る文面を見られる |
| 記録と戻し | 公開・変更は監査ログに残す。前の版に戻せる(戻すのも新しい版として公開) |
| 編集できる人 | テナントの `admin` だけ(権限 `records.template.edit` を `admin` にだけ付ける)。事務所の人(`office`)・スタッフは見るだけ |

AI のプロンプト(版つき・既定に戻す・履歴)と言葉の表(xlsx の書き出し・取込、試してから適用)は、katahimo-app の管理画面の作りをそのまま移す。今キューテスト様が手を入れているのはこの2つなので、ここは操作の手順も変えない。

### 4.2 記録AI の一般化

katahimo-app の「子どもの年齢帯 × 家庭の教育思考★ × PSI で語句を絞る」を、次の3つの組み合わせにする。

- **評価尺度**(`assessment_scales`、事業ごと): 段階・名前・説明。PSI・ES(1〜5)、教育思考★(1〜5)、要介護度、ADL などを同じ表で持つ。値は対象者・世帯・記録のどれかに付く。
- **条件付きの語句**(`ai_phrase_entries`): 語句・種類・条件(対象者の年齢の範囲、尺度の値の範囲、サービス種別)・並び順。今の `report_keywords` / `report_phrases` / `report_age_bands` はこの1つにまとまる。
- **調整の規則**(`ai_adjust_rules`): 「PSI が 3 なら教育思考を1段下げ、専門用語を禁止」のような規則。書ける形(条件 → 尺度の補正 / 語句の種類の禁止 / 警告の追加)はコードで決め、中身は子育て訪問の業種パックのデータにする。katahimo-app の `applyPsi` と同じ結果になることをテストで確かめる。

プロンプトのひな形(`{placeholder}` と `{#section}…{/section}`)、生成ログ、記録への紐づけ、保存期間はそのまま移す。

### 4.3 出力テンプレート(Excel)

- `export_templates`(テナントごと): 出力の種類(勤務表・記録の一覧・経費)、列(見出し・元の値・書式・Excel の式)、シートの名前の規則。
- katahimo-app の `sheetTemplate.ts`(列・式・キャッシュ値)は、この定義の1件「キューテスト様の出勤簿」になる。式の検算テスト(`testFormulaEvaluator.ts`、LibreOffice のテスト)は「テンプレートの定義に対する一般のテスト」として移す。
- 計算の正はドメイン(勤務時間・移動距離)。Excel の式は表示のための写しで、キャッシュ値はドメインの値から入れる(今と同じ)。

## 5. ログインの統一

**併用はしない。** 理由:

- パスワードの保管・再設定・回数制限・端末の信頼の仕組みを2系統持つことになり、守る面が倍になる。
- 管理職の MFA・退職時の無効化・招待制が片方にしか効かず、テナントごとに安全性が変わる。
- carevisit は「パスワードを自前で持たない」と決めている(設計書 §1.4)。キューテスト様だけを例外にすると、その例外がずっと残る。

**キューテスト様は Google ログインだけにする。** 全員が `@cutest.biz` の Google アカウントを持っているため。

- パスワードの再設定もハッシュの引き継ぎも要らない。スタッフは「Google でログイン」を押すだけ。
- 2段階認証・パスワードの決まり・退職時のアカウント停止は、キューテスト様の Google Workspace の設定がそのまま効く。carevisit 側でもスタッフを退職にすればセッションを失効し、Identity Platform のユーザーを無効にする(今の `retirement-sync`)。
- テナントの設定に「ログインできる方法」と「許すドメイン」を持たせる: キューテスト様は `google` だけ・`cutest.biz` だけ。Google の ID トークンの `hd`(Workspace のドメイン)が `cutest.biz` でなければ、blocking function(`beforeSignIn`)とサーバーの両方で拒否する。メールの末尾ではなく `hd` で見る(個人の Gmail に会社のアドレスを付けた別のアカウントを通さない)。
- 招待制は今のまま: 管理者がスタッフを登録すると、その `@cutest.biz` のアドレスだけがログインできる。
- 他のテナント(alca・フォールなど)は、今の carevisit のとおりメール+パスワードと Google を選べる。
- 予備: Google ログインが使えない事情が出たときに限り、GAS のハッシュ(`sha256(パスワード + 共通のソルト)`、`packages/core/src/domain/legacyAuth/computeLegacyHash.ts`)を Identity Platform に取り込む方法がある(SHA-256・パスワードが先の順で取込に対応している見込み。使うなら Emulator で確かめる)。

ログインの画面は変わる(URL が `/t/<slug>/login`、「Google でログイン」のボタン)。切替日の案内に入れる。

### 5.1 カレンダーの読み方(参考)

スタッフのカレンダーも `@cutest.biz` の Google カレンダー。今の katahimo-app と同じく、カレンダーをサービスアカウントに共有してもらい、読めるカレンダーは運用担当が許可の一覧(`@cutest.biz` の末尾で許可)で決める。Google Workspace のドメイン全体の委任を使えば共有の手間は無くなるが、サービスアカウントにドメインの全員のカレンダーを読む権限を持たせることになるので、今は共有の方式のまま。

## 8. AI 分析の連携(MCP サーバーと分析用のひな形)

キューテスト様の担当者は、日報・出勤簿の一覧を Claude Code で分析している。今は GAS のシートを読んでいると思われるが、切替の後はアプリで完結するので、**アプリのデータを Claude Code から安全に読める口**を用意する。

### 8.1 方式の比較

| 方式 | 手間 | 新しさ | 個人情報の管理 | 判定 |
| --- | --- | --- | --- | --- |
| 画面から CSV を落として Claude Code に読ませる | 毎回の書き出し | 書き出した時点 | 担当者の PC に個人情報のファイルが残る | 予備(今の CSV の出力は残す) |
| API キー + 自作のスクリプト | スクリプトの保守が要る | 最新 | キューテスト様の側でキーの管理 | 採らない |
| **リモートの MCP サーバー** | Claude Code に1回登録するだけ | 最新 | アプリの権限・監査ログ・仮名化がそのまま効く | **採る** |

MCP(Model Context Protocol)は Claude Code が外部のデータ・道具につなぐ標準の方式。アプリ(API サービス)に MCP の口(`/mcp`、Streamable HTTP)を足すと、担当者は次の1行で使える。

```bash
claude mcp add --transport http carevisit https://<アプリのドメイン>/mcp
# 初回は Claude Code の /mcp からブラウザでログイン(Google の @cutest.biz)
```

### 8.2 MCP サーバーの設計

プラットフォームのモジュール `analytics-mcp` として作り、どのテナントでも使える形にする。

- **認証**: MCP の認可の仕様(OAuth 2.1 + PKCE)に従う。認可サーバーはアプリが持ち、ログインはアプリと同じ Identity Platform(キューテスト様は `@cutest.biz` の Google ログイン、管理職は MFA)。アクセストークンは1時間、更新トークンは30日で使うたびに替える。トークンはテナント・スタッフに結びつき、スタッフの退職・権限の変更・管理画面の「連携を切る」で無効になる。
- **使える人**: 権限 `analytics.read` を持つ人。既定は `admin` だけ(事務所の人に開くかはテナントの設定)。スタッフは使えない。
- **読むだけ**: 書き込む道具は作らない。
- **テナントの外は見えない**: 1回の呼び出しごとに今と同じ UoW(RLS)で読む。テナントはトークンからだけ決める。
- **監査**: 呼び出しごとに監査ログ(`analytics.mcp.called`: 道具の名前・期間・件数。中身は書かない)。管理画面に「AI 分析の利用の記録」を出す。
- **回数・量の上限**: 1回の応答の行数・文字数の上限(Claude の文脈に収める)、1時間あたりの呼び出しの上限。

### 8.3 道具(tools)とデータセット

データは「データセット」として各モジュールが登録する(`records` が報告、`timesheet` が勤務表…)。MCP の道具はデータセットに共通の形にする。

| 道具 | 中身 |
| --- | --- |
| `list_datasets` | 使えるデータセット・列・意味・単位の一覧(データの辞書) |
| `query_dataset` | 期間・スタッフ・利用者・事業・ひな形の項目での絞り込み、列の選択、ページ送り |
| `aggregate_dataset` | 件数・合計・平均を、日・週・月・スタッフ・利用者・事業で集計(大きなデータはサーバーで集計してから渡す) |
| `get_record` | 報告1件の全文(改版の履歴つき) |
| `export_dataset` | 件数の多い分析のための書き出し。1回だけ・5分で切れる URL を返し、Claude Code がファイルに保存して Python などで分析する(監査ログに残す) |

最初に用意するデータセット:

| データセット | 中身 | 出どころ |
| --- | --- | --- |
| `daily_reports` | 日付・時間・スタッフ・利用者(仮名)・対象児の月齢・本文(社内向け・保護者向け)・PSI・ES・教育思考★・AI が使った言葉 | `records`、`record-ai` |
| `incident_reports` | 事故・ヒヤリハット | `records` |
| `timesheet_days` | 日ごとの訪問・勤務時間・移動距離・事務作業・買物代行など(出勤簿の内容) | `timesheet` |
| `timesheet_months` | 月の合計(今月のまとめと同じ値) | `timesheet` |
| `expenses` | 領収書の金額・区分(お客様請求 / 会社負担)・取消を除く | `expenses` |
| `visits` | 予定と実績(割当て・打刻) | core・`field` |

### 8.4 個人情報の扱い

日報には子どもの様子・家庭の状況・PSI が入る。Claude に渡す前提で、次を守る。

- **既定は仮名**: 利用者・対象児は `C-0123` のような仮の番号、スタッフは名前(社内の分析で要るため。テナントの設定で仮名にもできる)。住所・電話・メール・生年月日(月齢に変える)・アレルギーの詳細は出さない。本文の中の名前は、登録してある利用者・家族・子どもの名前を仮の番号に置き換える(完全ではないことを担当者向けの説明に書く)。
- **実名で見たいとき**: 権限 `analytics.read.identified` を持つ人だけ、道具の引数で実名に切り替えられる。切り替えは監査ログに残す。
- **要配慮の項目**: ひな形で「要配慮」の印を付けた項目(看護記録の病歴など)は既定で出さない。
- **Claude の契約**: 業務のデータを渡すので、キューテスト様の Claude は、入力を学習に使わない法人向けの契約(Team / Enterprise、または API の商用の契約)で使ってもらう。利用規約・個人情報の取扱いの説明(利用目的に「サービスの質の改善のための分析」を入れる)はキューテスト様の側で確認してもらう。

### 8.5 分析用のひな形(キューテスト様に渡すもの)

「つなぐだけ」で分析を始められるよう、Claude Code のプロジェクトのひな形を用意する(carevisit の `tools/analysis-kit/`。テナントごとの設定を入れて渡す)。

```
analysis-kit/
├─ .mcp.json              # MCP サーバーの登録(URL だけ。トークンは各自のログインで入る)
├─ CLAUDE.md              # データセットの説明、仮名の決まり、出力の置き場所、やってはいけないこと
├─ .claude/
│  ├─ settings.json       # MCP の道具の許可、ファイルの書き出し先の制限
│  └─ skills/
│     ├─ monthly-report-review/   # 月次の日報の傾向(PSI の推移・気になる家庭・言葉の使われ方)
│     ├─ staff-workload/          # スタッフ別の勤務時間・移動・訪問件数
│     ├─ psi-followup/            # PSI が下がった家庭の一覧と経過
│     └─ expense-summary/         # 立替経費の月次の集計
├─ outputs/               # 分析の結果(.gitignore。個人情報を含みうる)
└─ README.md              # 使い方(1行の登録・ログイン・スキルの呼び方)
```

- スキル(分析の手順書)は、キューテスト様の担当者が今 Claude Code でしている分析を聞き取って作る。担当者が自分でスキルを足せる。
- MCP のプロンプト(`prompts`)にも同じ分析の型を載せ、Claude Code 以外(Claude のアプリのコネクタ)からも使えるようにする。
- 他のテナントにも同じひな形を使える。業種パックごとにスキルの既定を持つ(訪問介護なら「サービス提供記録の記載漏れ」など)。
